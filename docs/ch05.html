第 5 章 · 技巧工具箱

提示工程技巧

上一章讲了“好 prompt 长什么样”，这一章给你一整套实战技巧：让模型从邮件里抽数据、给聊天记录脱敏、 扮演特定角色、照着示例回答、一步步推理，以及把大任务拆成一串小 prompt。

本章目标

  • 用指令提示做数据抽取、PII 脱敏、合成数据生成
  • 用 persona（角色）隐式地收窄模型的回答范围
  • 掌握 zero-shot / one-shot / few-shot，用示例“教”模型
  • 理解思维链（CoT）为什么有效，以及它的代价
  • 学会提示链（prompt chaining）和几条实用的最佳实践
💡 学习建议
  • 亲手试每个例子：第 3 章的服务、Ollama 命令行、ChatGPT 都行，还可以把几种技巧组合起来。
  • 想想用传统代码怎么做：当你想象用正则和规则实现同样功能有多痛苦时，就会真正体会到 LLM 的价值。

提示工程仍是一个开放的研究领域，不同模型偏好的写法可能不同。下面是作者在实践中最有用的一批。

指令提示：三个实用场景

LLM 的好坏取决于你给它的指令。指令写对了，它能做数据抽取、PII 脱敏、文本分类…… 不需要庞大的标注数据集，也不需要写在代码里一碰就碎的规则。

场景 1：从非结构化文本里抽数据

据估计，企业里 80–90% 的数据是非结构化的：邮件、PDF、Word、聊天记录…… 正则表达式在格式一变时就会失效，而 LLM 能理解文字的含义： 它知道 “Sarah Whitfield, Director of Customer Experience” 里既有姓名又有职位， 知道 “$1,565 due by 12/1/2025” 里有金额和日期 —— 即使这些字段没有任何标签。

Prompt · Llama 3.2 3B
Given the following email: Hi Jacob, Thank you for sending over the detailed proposal. I've reviewed it with our product and customer success leads, and we're excited about the project. Please put together an SOW for review so we can get things started. We'd like you to travel to our office in Denver, Colorado, for the kick off meeting. Thanks again for the thorough proposal. I'm looking forward to collaborating. Best regards, Sarah Whitfield Director of Customer Experience Acme Software Solutions sarah.whitfield@acmesoft.com · (312) 555-0182 Extract the sender's name, location, and job_title, company, email, and phone_number. Provide the results back in JSON format where each data element is an attribute. Only return the JSON in your response.
{"sender_name": "Sarah Whitfield", "location": "Denver, Colorado", "job_title": "Director of Customer Experience", "company": "Acme Software Solutions", "email": "sarah.whitfield@acmesoft.com", "phone_number": "(312) 555-0182"}
  • 模型只凭最少的指令就提取出了联系方式。
  • 它照搬了你的命名风格：prompt 里写 job_title、phone_number 用了下划线，输出也用下划线。
⚠ 两个隐患
  • 模型在做假设：Sarah 只说“来我们 Denver 的办公室”，并没说自己在那。根据用例，你可能需要更具体的指令、字段说明或示例。
  • 格式没有保证：自己偶尔用用没问题，但代码需要每次都一致的 JSON。第 6 章的结构化输出会解决这个问题。

场景 2：PII 脱敏

保护个人身份信息（PII）往往是法律要求。正则能去掉已知格式（如身份证号），但常常漏掉边缘情况和格式变体。 LLM 能凭语义理解，识别出正则认不出的“换了种说法的 PII”。

⚠ 先想清楚数据去了哪

把含敏感信息的 prompt 发给 LLM 之前，先搞清楚数据的生命周期：用托管 API，要确认服务商怎么保护你的数据、 会不会拿你的 prompt 去训练模型；用自托管模型，要确保自己没有把 prompt 记到日志里。

Prompt
Given the following customer chat, redact any personally identifiable information (PII) and replace it with a placeholder (for example, [name]). Redact the following data: name, phone number, email, and address. <chat> Agent: Hi Jacob, welcome to Customer First Bank. How can I help you today? Customer: I need to order new checks. Agent: Sure, I can help you with that. Can you verify a few things for me? I need your phone number and your address. Customer: Sure. My phone number is 214-555-1234 and my address is 1234 Fake St, Dallas, TX 75002. Agent: Perfect. I've ordered you a new set of checks that will be shipped to your address. You will receive a confirmation email at: jacob.orshalick@email.com. Customer: Thanks! </chat> Only return the <chat> content with the PII redacted.

这里用了两个小技巧：

  1. 一个示例胜过千言：只写了 [name]，模型就明白了 [phone number]、[email] 该怎么写。
  2. 分隔符：用 XML 标签 <chat>…</chat> 标出聊天内容的起止，让模型不会把聊天当成指令。

场景 3：生成合成数据

开发、测试、演示、压测、复现 bug……很多时候你需要“看起来真实但不是真的”的数据。LLM 很擅长生成 JSON、CSV、SQL INSERT 等格式的合成数据， 而且不用碰生产数据。下面这个 prompt 生成了第 7 章要用的商品数据：

The CSV should have the following headers and columns, in this exact order: - product_id - title - category - description - price The first row must be the header. The total number of rows (including the header) should be 31. Do not repeat any product_id. The output should be valid CSV format, with all fields properly quoted if necessary. 角色提示（Persona）

Persona 就是给 LLM 一个身份，让它以那个人的视角回答。来做个实验： 问 “Can you tell me how to authenticate to Gmail?”，“authenticate（认证）”这个词在不同场景下意思完全不同。

Persona 利用了模型的预训练，相当于一次性给了它一大堆隐式指令：

更紧的任务框定

少写很多显式指令，prompt 更简单。

更低的成本

prompt 越短，计费的 token 越少。

一致的语气

长对话里风格保持统一。

更安全

专业身份帮助限定话题范围（第 6 章护栏）。

角色可以非常具体，例如：“You are an accounting software integration engineer with extensive experience integrating QuickBooks APIs.”

⚠ 慎用医生、律师、理财顾问这类角色

它们暗示了受监管领域的专业资质。如果用户把模型的回答当成专业建议，可能引发法律或伦理问题。务必明确说明 AI 不是持证专家，回答仅供参考。

Zero-shot、One-shot、Few-shot

通过示例来教，是一种上下文内学习（in-context learning）。LLM 天生就是好学生：

Zero-shot 零样本只给指令，完全靠模型的预训练。
One-shot 单样本给一个示例，示范怎么回答。
Few-shot 少样本给多个示例，覆盖各种情况。

回到第 4 章的情感分析。零样本时，模型可能回答 Sentiment: Positive、Positive 或 The statement is positive —— 技术上都对，但你的代码没法稳定解析。加上几个示例看看：

Few-shot Prompt
<instructions> You are an expert on sentiment analysis. You will analyze a statement and respond with the sentiment as positive, negative, or neutral. </instructions> <examples> User: Thank you @AcmeCorp! This new shampoo has been great! Assistant: positive User: My order from @AcmeCorp never arrived and customer service wasn't helpful. Assistant: negative User: I wouldn't trust @AcmeCorp. Assistant: negative </examples> User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great. Assistant:
positive

注意示例里用了通用的角色名 User 和 Assistant —— 下一章你会看到，从代码调 API 时，角色是一等公民。 用预训练模型做分类时，准确性取决于两点：模型怎么训练的，以及示例的数量和多样性。 这里模型本来就懂“情感”，示例只是在规定输出形式。

进阶：分类到“模型不知道”的类别

假设要把社媒评论路由到对应部门，自动开工单。公司有哪些部门是内部知识，模型从没学过。 没关系 —— 这仍然是分类问题，在 prompt 里给出标签清单 + 每个标签的说明 + 示例就行：

Few-shot Prompt · 情感 + 部门路由
<instructions> You are an online customer feedback expert. Analyze the provided statement carefully and respond with the sentiment as positive, negative, or neutral. Specify the department the statement should be routed to: - customer_support: issues with customer support not being helpful - online_ordering: issues with ordering, website speed, or checkout process - product_quality: issues with product quality or description - shipping_and_delivery: issues with slow shipping or not receiving an order - other_off_topic: a department could not be identified Only respond with JSON that includes the sentiment and the department based on the <examples> provided. </instructions> <examples> User: Thank you @AcmeCorp! This new shampoo has been great! Assistant: {"sentiment"="positive","department"="product_quality"} User: My order from @AcmeCorp never arrived and customer service wasn't helpful. Assistant: {"sentiment"="negative","department"="customer_support"} User: I wouldn't trust @AcmeCorp. Assistant: {"sentiment"="negative","department"="other_off_topic"} User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great. Assistant: {"sentiment"="positive","department"="shipping_and_delivery"} User: The @AcmeCorp website is so slow. Every time I've tried to order I can't even get through checkout. Assistant: {"sentiment"="negative","department"="online_ordering"} </examples> User: Don't trust @AcmeCorp. It's been weeks and my order was never even shipped! Assistant:
{"sentiment": "negative", "department": "shipping_and_delivery"}
ⓘ 什么时候该微调？

如果模型对某类标签非常陌生，可能要给多到上下文窗口都塞不下的示例才能教会它。这时微调才划算 —— 第四部分会看一个给邮件打自定义标签的例子。另外，即使示例再多，JSON 格式也仍不能保证，要靠第 6 章的结构化输出。

🔑 分隔符（Delimiters）

上面用 XML 标签把 <instructions> 和 <examples> 包了起来。 分隔符帮模型分清“哪部分是指令、哪部分是资料、哪部分是示例”。没有统一标准，XML 标签、引号、Markdown 标题都好用， 用你的模型和内容实验一下。

思维链（Chain-of-Thought）

你有没有发现，LLM 有时能解出很难的题，却数不清 “strawberry” 里有几个 r？ 因为 LLM 并不会像人一样自动把问题拆成步骤。它默认会根据见过的模式直接“跳”到最终答案。

思维链（CoT）就是鼓励模型一步步来，像编程面试时在白板上边写边讲。触发它很简单：

  1. 直接告诉它：“Think step-by-step.”
  2. 或者在示例里展示多步推理的过程。
🔑 为什么有效？

回忆第 1 章：模型生成的每个 token 都会被追加到上下文，用于下一次预测。 所以让模型先写出推理步骤，相当于它先向自己解释了问题该怎么解，再给出答案。 这也是 Agent 里最常用的提示技巧之一 —— 它帮模型推理出完成目标需要哪些步骤（第五部分）。

代价与替代方案

考量说明
推理有成本更多 token = 更慢 + 更贵
模型推理能力各不相同同样的写法，不同模型效果可能差很多
“大声思考”有风险推理过程可能泄露敏感数据、内部假设或偏见

推理模型（如 GPT-5 家族）即使不专门提示也会“思考”：回答前先生成推理 token， 你甚至能展开它的“草稿纸”看它怎么得出结论 —— 验证回答时很有用。但这些 token 同样要计费、同样拖慢响应。

草稿链（Chain of Draft，CoD）是 CoT 的精简版：让模型每一步只写最核心的几个词。

CoD 指令
Think step-by-step but keep only a minimal draft for each step, with five words at most.
⚠ 生产环境：考虑隐藏思维链

让模型把推理过程直接展示给用户，可能意外泄露敏感信息或内部假设。 很多系统使用隐藏思维链（hidden CoT）：模型在内部推理，只把最终答案返回给用户。

提示链（Prompt Chaining）

与其写一个什么都要做的巨型 prompt，不如把任务拆成一串小步骤，每一步一个聚焦的 prompt， 上一步的输出作为下一步的输入。这和写代码时把大函数拆成小函数是一个道理。

好处说明
子任务范围小每个 prompt 只做一件事，模型不用一次面对整个问题
明确的输入输出约定每一步定义好 schema，便于校验、替换、复用
好调试检查中间输出就能定位出错环节，不用在巨型 prompt 里瞎猜
组件复用一个测试良好的“抽取邮件字段” prompt，工单分诊和销售线索两处都能用
更省 token、更快每一步只看它需要的数据
内建护栏步骤之间插入 JSON 校验、事实性打分等，在错误扩散前拦住
推理透明中间结果形成审计轨迹，对合规审查、向他人解释都很有价值

RAG 流水线、Agent 等系统都建立在这个模式之上（第 8 章起）。

实用最佳实践

1. 用正面表述，少用“不要”

✗ 负面表述
Do not include sentiment: in your response.
✓ 正面表述
Respond only with the sentiment value: positive, neutral, or negative.

负面说法迫使模型去推断“你想要的反面是什么”，容易出错。正面指令更短、更容易检查，模型也更能一致地遵守。

2. 和模型一起打磨 prompt（顺着偏见走）

你也可以直接问模型：“为了得到这样的结果，我该怎么改进这个 prompt？” 把输入输出示例一起给它，让它帮你写 prompt。

3. 把 prompt 当代码管理

好工程师的习惯：只要跑通了，哪怕是很小的改动也提交。对 prompt 一视同仁 —— 放进 Git 或专门的 prompt 管理工具，这样你总能回退到上一个可用版本，放心大胆地实验。

4. 系统地测试 prompt 变体

措辞的细微变化能彻底改变回答质量。可以自己对比，也可以用 PromptLayer 这类工具：

方法说明
A/B 测试两个 prompt 版本正面对决，看哪个质量更高
人工审阅抽样让领域专家评价清晰度、正确性、语气
跨模型评估同一 prompt 发给 GPT-5 mini、Claude Haiku 4.5、Llama 3.2，选最合适的
回归基线锁定一组“已知良好”的 prompt + 模型，定期重跑，检测模型更新后的质量漂移
自动指标文本相似度用 BLEU / ROUGE，分类用准确率 / F1，无需人工也能打分

小结

技巧核心
指令提示简洁、正面的指令就能做数据抽取、PII 脱敏、合成数据，不用手写解析器
角色提示一个身份 = 一堆隐式指令：收窄范围、统一语气、节省 token
Zero / One / Few-shot用示例教模型认识你的标签和输出格式
思维链 CoT让模型一步步推理，用更多 token 换更好的逻辑和透明度
草稿链 CoDCoT 的精简版，控制延迟和成本
提示链像组合函数一样串联 prompt，模块化、可复用、可审计
最佳实践正面表述、和模型协作迭代、版本管理、系统化测试

动手练习

  1. 把情感分析 prompt 做成 zero-shot、one-shot、few-shot 三个版本，拿同一批帖子测试，记录各自答对了几条。
  2. 用三个角色问 “How do I reset my password?”：安全工程师、客服代表、幼儿园老师。比较语气、深度和恰当性。
  3. 串联两个 prompt：(a) 从一段新闻中抽取关键事实；(b) 根据事实写一句话摘要。和一个大 prompt 一步到位的结果比较，哪个更好？
