Embedding 模型和 LLM 一样在海量文本上训练，通过词语在不同上下文中如何一起出现来学到含义， 然后把文字编码成机器友好的数字。它们本来就是 LLM 的基础部件，但我们也可以直接拿来用。

关键词搜索的局限

假设你想在商品库里找“冬天穿的厚外套”，用 SQL 大概会这样写：

-- 方式 1：字面匹配
SELECT * FROM product_descriptions WHERE description LIKE '%winter jacket%';

-- 方式 2：全文搜索（能处理词形变化和部分同义词）
SELECT * FROM product_descriptions
WHERE MATCH(description) AGAINST('winter jacket' IN NATURAL LANGUAGE MODE);

向量数据库用 embedding 模型把文字（甚至图片、音频）的含义编码成一组数字，这组数字叫向量嵌入（vector embedding）。 于是我们可以按“意思有多接近”来搜索。

💡 先看看你现有的数据库

PostgreSQL（pgvector 扩展）、MongoDB、Cassandra 等已经直接或通过扩展支持向量。需要相似性搜索时，先检查现有数据库能不能做，再考虑引入专门的向量数据库。

理解向量嵌入

Embedding 模型是一种专门的神经网络，把人能理解的数据转成一串定长的浮点数。 对我们来说它就是一个数组；对模型来说，它是高维空间里的一个点。

把知识库文章都画成空间里的点，意思相近的文章会聚在一起。用户的问题也变成一个点，离它最近的文章就是最相关的：

维度是什么？用水果来理解

向量里的每个数字是一个维度，代表模型学到的某个特征，数值表示数据和这个特征有多吻合。 假设有一个专门描述水果的三维空间：甜度、大小、柑橘味。

⚠ 真实的维度没有“人话”含义

水果的例子只是帮助理解。现实中每个维度是模型在训练中自己学到的特征，我们并不知道它们代表什么。 我们只知道：两个点越近，原始数据的意思越相似。一般来说维度越多，模型越准确。

Embedding 模型维度说明
text-embedding-ada-0021,536仅文本
text-embedding-3-small1,536（可降到 512）仅文本，比 ada-002 更准
text-embedding-3-large3,072（可降到 256 / 1,024）最准；支持“套娃（matryoshka）”缩放以加快搜索
clip-ViT-B-32512多模态：文字和图片在同一个空间

多模态模型很神奇：文字 “apple” 和一张苹果照片的 embedding 会落在彼此附近 —— 它们只是同一个事物的两种表示。

用 Sentence Transformers 生成 embedding

Chroma 默认用 SBERT（Sentence-BERT），它是 BERT 的一个变体，专门把整个句子转成向量。 SBERT 通过 Hugging Face 维护的 Sentence Transformers 库分发。 

pip install sentence-transformers==5.1.2

from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")      # ❶ 速度、体积、效果平衡得很好

sentences = [
    "Sony Wireless Noise-Canceling Headphones",
    "Canon Professional DSLR Camera Kit",
    "Jenson Wireless Earbuds Pro",
    "Panasonic Wireless Noise-Reduction Headphones",
]

embeddings = model.encode(sentences)                 # 一次编码所有句子

print(embeddings[0])                                 # [ 9.95e-02  4.46e-02  2.07e-03 ... ]
print(f"Dimensions: {len(embeddings[0])}")           # Dimensions: 384

# 计算第 0 句和所有句子的相似度
similarities = model.similarity(embeddings[0], embeddings)
for idx, embedding in enumerate(embeddings):         # enumerate：同时拿到下标和元素
    print(f"- {sentences[idx]}, Score: {similarities[0][idx]:.4f}")   # :.4f 保留 4 位小数

实际开发中我们不会自己算距离 —— 交给向量数据库。但理解底层原理，能帮你在结果不对劲时找到原因。

怎么选 embedding 模型

Embedding 模型的选择会显著影响结果：它们为特定目的训练，关注的特征可能完全不同，还带着训练数据的偏见。

问题考量
嵌入什么数据？文本用 Sentence Transformers；图片、音频需要多模态模型
什么领域？医学、法律等专业文本，考虑在该领域训练过的模型
要达成什么？做商品推荐，就要能深度理解商品描述的模型
什么语言？需要多语言就选支持多语言输入的模型
性能要求？有的模型为推理速度优化，适合实时场景，但可能牺牲准确性
支持度如何？开放权重看社区、文档、许可证；商业模型看厂商是否稳定
能否微调？打算适配领域需求时很关键（第四部分）
成本？大模型 token 或算力成本更高；维度越多，存储也越多
每次最多多少 token？embedding 模型的输入上限通常远小于 LLM，第 8 章用分块解决

去哪找：托管 API 厂商会给你几个选项；开放权重模型去 Hugging Face（超过一百万个模型，可以按库 sentence-transformers 筛选）； 也可以先看 Hugging Face Embedding Leaderboard（MTEB 排行榜）挑几个候选，再用自己的数据实验。

读懂模型名称

模型名就像 AI 的身份证：谁做的、什么家族、多大、经过什么训练和优化，都写在用连字符隔开的片段里。

片段含义例子
27b / 4b / 70B参数量（十亿）。参数是训练中被调整的内部数值gemma-3-27b-pt
ptPretrained：只做了预训练的原始基座，没为对话调优gemma-3-27b-pt
itInstruction-tuned：更擅长听指令、对话。做聊天机器人通常选它gemma-3-27b-it
qat量化感知训练：训练时就考虑了量化，量化后性能损失更小gemma-3-4b-it-qat-…
q4_04 位量化：用 4 位而不是 16/32 位表示参数，体积更小、推理更快…-q4_0-gguf
gguf为本地高效推理优化的文件格式…-gguf
uncased训练时忽略大小写（Apple 和 apple 一样）distilbert-base-uncased
finetuned-sst-2在 SST-2（斯坦福情感树库）上微调过 → 擅长情感分析distilbert-base-uncased-finetuned-sst-2-english
Distill知识蒸馏：小“学生”模型模仿大“老师”模型DeepSeek-R1-Distill-Llama-70B

向量数据库怎么检索

向量数据库专门用来存储海量向量、并高效计算它们之间的距离。用在 RAG 里的完整流程是三步：

最近邻：精确（ENN）还是近似（ANN）

查询时，数据库返回离问题最近的 k 个邻居（k-NN）。最笨的办法是算出和每一个向量的距离 —— 这叫精确最近邻（ENN），结果保证准确，但数据一多就慢得无法接受。 所以向量数据库通常用近似最近邻（ANN）：借助索引和聚类等捷径，只搜“最可能”的区域。

实战一：语义搜索

  1. 读取商品数据从 products.csv 加载所有商品。
  2. 准备 embedding 函数使用 all-MiniLM-L6-v2。
  3. 创建 collection告诉 Chroma 用哪个 embedding 函数。
  4. 拼接文本把每个商品的标题和描述合成一段文字。
  5. 写入文本 + 元数据 + ID 一起存进去，Chroma 自动生成 embedding。
  6. 查询用自然语言提问，拿回最相近的 k 个商品。
pip install chromadb==1.2.1 pandas==2.3.3 numpy==1.26.4

import chromadb
from chromadb.utils import embedding_functions
import pandas as pd

client = chromadb.Client()                    # 临时（内存）客户端，程序退出数据就没了

embedding_function = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="all-MiniLM-L6-v2"
)

collection = client.create_collection(
    name="product_search",
    embedding_function=embedding_function     # collection 会替我们生成 embedding
)

products_df = pd.read_csv('products.csv')                          # DataFrame：按列名取数据
all_titles_and_descriptions = zip(products_df['title'], products_df['description'])
texts = [f"{title} {desc}" for title, desc in all_titles_and_descriptions]   # 列表推导式

一个 Chroma collection 就像一张表，每条记录有四部分：

collection.add(
    documents=texts,
    metadatas=[{                                   # 元数据：之后可以过滤、展示
        'product_id': pid, 'title': title, 'category': category, 'price': price,
    } for pid, title, category, price in zip(
        products_df['product_id'], products_df['title'],
        products_df['category'], products_df['price']
    )],
    ids=[pid for pid in products_df['product_id']]  # 每条记录必须有唯一 ID
)

query = "camera for taking professional looking photos"
results = collection.query(query_texts=[query], n_results=3)   # n_results 就是 k-NN 里的 k

for metadata in results['metadatas'][0]:
    print(f"{metadata['product_id']}: {metadata['title']}")

实战二：推荐引擎

既然每个 embedding 都“懂”商品的意思，那么拿用户买过的商品去查询，就能找到他可能感兴趣的相似商品。

简单

不用训练机器学习模型，直接用预训练 embedding。

可解释

能清楚看到推荐和哪件已购商品最相似。

灵活

新商品、新类别直接加入，无需重新训练。

可打分

相关性 = 相似度 + 类别等业务规则。

from dataclasses import dataclass, field
from typing import List

@dataclass                                   # 自动生成 __init__、__repr__、__eq__
class Product:
    product_id: str
    title: str
    category: str
    description: str
    price: float

    def title_and_description(self) -> str:
        return f"{self.title} {self.description}"

@dataclass
class PurchaseHistory:
    products: List[Product] = field(default_factory=list)   # 每个实例都有自己的新列表

    def has_purchased_product(self, product_id: str) -> bool:
        return any(product.product_id == product_id for product in self.products)

    def get_purchase_descriptions(self) -> List[str]:
        return [product.title_and_description() for product in self.products]
👉 @dataclass vs Pydantic

Pydantic 模型会做校验，适合和外部系统打交道；@dataclass 是 Python 自带的简单“数据容器”，自动生成构造器等样板方法，适合内部使用。

def get_recommendations(self, purchase_history: PurchaseHistory,
                        n_recommendations: int = 3,
                        same_category_weight: float = 0.7) -> List[Product]:
    if not purchase_history.products:
        return []

    results = self.collection.query(
        query_texts=purchase_history.get_purchase_descriptions(),
        n_results=n_recommendations + len(purchase_history)    # 多取：已购商品会排在最前
    )

    recommendations = []
    for idx, metadata in enumerate(results['metadatas'][0]):
        product_id = metadata['product_id']

        if purchase_history.has_purchased_product(product_id):  # 跳过已购
            continue

        category_bonus = same_category_weight if any(           # 同类别加分
            p.category == metadata['category'] for p in purchase_history.products
        ) else 0

        product = self.find_product(product_id)
        product.relevance_score = results['distances'][0][idx] + category_bonus
        recommendations.append(product)

        if len(recommendations) >= n_recommendations:
            break

    recommendations.sort(key=lambda x: x.relevance_score)       # 分数越低越相关
    return recommendations

元数据过滤

纯相似度只是故事的一部分。真实推荐还要考虑用户的其他信息 —— 比如别给住在市中心、从不买户外用品的人推荐登山靴。 where 过滤器的用法很像 SQL 的 WHERE： 

purchase_categories = [product.category for product in purchase_history.products]

results = self.collection.query(
    query_texts=purchase_history.get_purchase_descriptions(),
    n_results=n_recommendations,
    where={"category": {"$in": purchase_categories}}   # 只在用户买过的类别里找
)
类型操作符例子
逻辑$and、$orElectronics 且低于 $100
比较$eq、$gt、$lt价格大于 50
集合$in、$nin类别属于 [books, games]

还可以用 where_document 按文档内容过滤，Chroma 也支持把全文搜索和向量搜索结合起来。
