第 8 章 · 检索增强生成

设计 RAG 系统

LLM 很强，但面对你自己的数据时它是一张白纸：内部 wiki、客服工单、数据库记录，它一概不知。 RAG（Retrieval-Augmented Generation，检索增强生成）就是解决这个问题的架构模式： 在需要的那一刻，把私有数据里恰好相关的那几段交给模型。

本章目标

  • 理解 RAG 流水线的两个阶段：摄取（离线）和推理（在线）
  • 掌握分块（chunking）策略，尤其是递归分块
  • 从零搭一个文档问答机器人：向量库 + prompt 模板 + 对话历史 + 流式
  • 给回答加上引用来源，提升可信度
  • 了解进阶技巧：父子检索、查询重写、重排序、混合检索、LLM 评判者
  • 重视 RAG 系统的数据质量与安全

什么是 RAG

在 ChatGPT 里做个对比实验：

🔮 RAG 与工具调用

模型怎么知道自己需要搜索？ChatGPT 在幕后把你的 prompt 和一组工具（名称、输入格式、使用说明）一起交给模型。 如果模型判断问题需要外部知识，就会调用“网页搜索”工具，拿到结果后再回答 —— 这个“检索然后生成”的过程就是 RAG。 也有系统在调用模型之前就先检索。工具调用在第五部分详细讲。

知识库：LLM 的外部记忆

把 RAG 用到客服场景：知识库存放所有 how-to 文章。往知识库里加文章，AI 客服就“学会”了新知识，不用重新训练。 而好的 RAG 只检索必要的内容，所以不用担心 prompt 太大或太贵。

🔑 RAG 的本质是上下文工程

RAG 不只是把文档塞进 prompt，而是塑造上下文：只让模型看到重要的内容，并以最清晰的形式呈现。好的上下文工程能降低成本、减少幻觉，并可测量地提升回答质量。

为什么用向量数据库？因为 “I'm having password issues”、“Something is wrong and I can't log in”、“I can't seem to sign in” 说的是同一件事，只有按含义检索才能都找到对的文章（第 7 章）。

RAG 流水线

一条 RAG 流水线分成两段：摄取提前离线做好，推理在每次用户提问时实时运行。

阶段做什么
分块收集文档，切成便于搜索的小片段（chunk）
嵌入与索引每个 chunk 转成向量存进数据库，建立索引以便快速检索
① 检索把用户问题做相似度搜索，拿回最相关的 top k 个 chunk
② 增强用 prompt 模板把系统指令、chunk 和问题拼在一起
③ 生成发给 LLM 生成回答

分块（Chunking）

分块策略的好坏直接决定 RAG 是否可靠。它要同时满足三个目标：

  1. embedding 能准确捕获这段文字的含义
  2. chunk 里有足够的上下文
  3. 长度不超过 embedding 模型的 token 上限

chunk 越小，包含的主题越少，embedding 的含义就越聚焦，检索也越准；检索结果发给 LLM 的 token 也更少、更相关。

最朴素的：按字符数硬切

from langchain_text_splitters import CharacterTextSplitter

text = """Our system requires multi-factor Authentication (MFA). This helps
to keep your account secure. This step-by-step guide will walk you through
the MFA setup."""

splitter = CharacterTextSplitter(
    separator="",          # 分隔符：空串表示可以在任意字符处切
    chunk_size=70,         # 每块 70 个字符
    chunk_overlap=20       # 相邻块重叠 20 个字符
)

for idx, chunk in enumerate(splitter.split_text(text)):
    print(f"{idx + 1}: {chunk}\n- character count: {len(chunk)}")

五种分块策略

策略说明
固定大小 Fixed size按字符数硬切。一般不推荐，但有助于理解
递归 Recursive ⭐最好的通用起点。按段落、换行、空格等常见分隔符逐级切，块大小不一，但更可能保留完整的意思
基于文档 Document based本质是递归，但按文档类型（Markdown、HTML、PDF）使用专门的分隔符
语义 Semantic用句子 embedding 找出语义相关的内容组成块。更慢、更耗算力
Agentic让 Agent 来分块。目前偏实验性，慢且难扩展

递归分块

RecursiveCharacterTextSplitter 先尝试按段落切，块还太大就换下一级分隔符继续切，直到满足大小要求：

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", ".", " ", ""],   # ❶ 加入了句号
    chunk_size=70,
    chunk_overlap=0,                            # ❷ 不重叠
    keep_separator='end'                        # 句号留在句尾
)

chunks = splitter.split_text(text)

搭一个最基础的 RAG

加载向量数据库

import chromadb
from chromadb import Collection
from chromadb.utils.embedding_functions.ollama_embedding_function import (
    OllamaEmbeddingFunction
)

class DocumentVectorStore:
    def __init__(self, document_text: str):
        ollama_embedding_function = OllamaEmbeddingFunction(
            url="http://localhost:11434",
            model_name="mxbai-embed-large"          # 用 Ollama 生成 embedding
        )

        client = chromadb.Client()
        self.collection: Collection = client.create_collection(
            name="examples_readme",
            embedding_function=ollama_embedding_function,
        )

        splitter = RecursiveCharacterTextSplitter.from_language(
            language="markdown", chunk_size=1500)
        chunks = splitter.split_text(document_text)

        self.collection.add(                        # 每个 chunk 都会触发一次 embedding
            documents=chunks,
            ids=[f"doc{chunk_idx + 1}" for chunk_idx, chunk in enumerate(chunks)]
        )

    def query(self, question: str, n_results=3) -> List[str]:
        results = self.collection.query(query_texts=[question], n_results=n_results)
        return results.get('documents')[0]

变成带对话历史的服务

@app.post("/")
def handle_post(chat_request: ChatRequest):
    question = chat_request.question

    conversation_history = ConversationHistory({          # 复用第 6 章的组件
        "role": "system",
        "content": system_message.render()
    })
    for msg in chat_request.history:
        conversation_history.add_message({'role': msg.role, 'content': msg.content})

    conversation_history.trim_history()                   # 控制历史长度

    documents = readme_vector_store.query(question)       # 检索

    conversation_history.add_message({                    # 检索结果渲染进 user 消息
        "role": "user",
        "content": user_message.render(documents=documents, question=question)
    })

    return StreamingResponse(
        generate_stream(conversation_history), media_type="text/plain")

引用来源：让用户能核实

用户不该因为回答听起来很自信就相信它，他们需要证据。引用来源（citation）回答了“这个信息从哪来的？”， 而且当模型必须给出依据时，它更倾向于引用真实文本而不是猜测，幻觉也会减少。

摄取时可以记录的来源信息包括：标题、作者或站点、原文链接、抓取日期，甚至精确位置（页、节、行）。

class Document(BaseModel):
    source_url: str
    content: str

def download_remote_document(owner="jorshali", repo="developers-guide-to-ai",
                             branch="main", filename="README.md") -> Document:
    source_url = f"https://github.com/{owner}/{repo}/blob/{branch}/{filename}"      # 给人看的链接
    raw_url = f"https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{filename}"  # 取纯文本
    response = requests.get(raw_url)
    response.raise_for_status()           # 4xx / 5xx 抛异常
    return Document(source_url=source_url, content=response.text)

for doc_idx, document in enumerate(documents):
    document_chunks = splitter.split_text(document.content)
    for chunk_idx, document_chunk in enumerate(document_chunks):
        self.collection.add(
            documents=document_chunk,
            ids=f"doc_{doc_idx + 1}_{chunk_idx + 1}",               # 文档号 + 块号
            metadatas={"source_url": document.source_url}           # 来源存为元数据
        )

进阶 RAG

到目前为止我们做的叫 naive RAG：简单、能用、很适合起步。需求增长后，你会碰到它的天花板。

更聪明的索引：父子检索与多向量

分块是个两难：小块对精确问题很准，但应付不了宽泛问题；大块上下文足，但对具体问题细节不够。

多向量检索则是为同一份文档生成多个 embedding（标题、摘要、小节标题、句子级块），都打上同一个文档 ID。 宽泛问题能命中高层 embedding，细节问题能命中句子级 embedding，最后聚合成原文档返回。

RAG 的几种架构变体

变体怎么工作什么时候用
Naive RAG经典向量检索，本章做的就是它中小型知识库、原型
混合检索关键词搜索 + 语义/向量搜索组合知识库大且杂、提问风格多样
CAG 缓存增强从内存缓存读而不是搜索索引；预加载到模型 KV 缓存，或直接用键值存储回答重复问题高流量、问题重复（FAQ 机器人）、要求超低延迟
API 增强LLM 发起工具调用（API）而不是搜索（本质是工具调用，第五部分）实时数据：天气、股价、库存
知识图谱 RAG事实存为相连的节点，沿关系精确取数高事实准确性、可追溯推理（合规、生物医学）

数据质量与安全

🔑 如果只记住一句话

更好的数据胜过更大的 prompt（better data beats bigger prompts）。上面每个技巧都建立在干净、最新、可信的数据之上。

🧹

从权威数据开始

统一格式、去掉样板文字；在文档和块两个层级都激进去重；记录版本、日期、权限、URL 等元数据。

📅

保持新鲜

定义什么算“当前”，归档过期副本，定期重建索引。

📈

可观测

记录查询、检索到的块和引用；跟踪命中率、延迟和答案质量。答案错了，靠日志调试流水线。

  • 没有合适的数据安全协议，不要把密钥或 PII 推送到第三方服务。
  • 处理敏感内容时，优先用本地或私有端点（比如本章的 Ollama + Chroma），并通过应用层控制访问。
  • 记录谁搜了什么、返回了哪些块、引用了哪些来源，保证可追溯。

小结

  1. 分块用基于文档类型的递归分块切分 README。
  2. 嵌入与索引用 mxbai-embed-large 生成 embedding，存进 Chroma。
  3. 模板system 消息负责角色、接地、不确定性处理；user 消息放上下文和问题。
  4. 组装服务检索 → 增强 → 流式生成，并带上对话历史。
  5. 引用把 source_url 一路带到回答里。

进阶方向：父子检索、查询重写、重排序、混合检索、LLM 评判者，以及 CAG、API 增强等架构变体。
