## 7.1 让机器理解我们的世界

机器是字面化的，它们用 1 和 0 "思考"。而自然语言复杂微妙——**词义取决于上下文**：

- "I'm going to the **bank** to deposit some money." → 银行
- "You'll catch more fish in this river if you walk down to the **bank**." → 河岸

**我们靠整个句子（上下文）理解指的是哪个 bank。**

> **要让机器理解自然语言，我们需要一种方式把词连同其上下文含义编码成机器友好的表示——这正是文本 embedding 模型被训练来做的事。**

和 LLM 一样，embedding 模型也在大量免费和授权数据上训练，**基于词在不同上下文中的共现方式捕获含义**。它们是 LLM 的基础组件，但我们也能直接利用它们。

## 7.2 关键词搜索的局限

早期搜索引擎依赖关键词（**lexical search，词法搜索**）。最好的开发者擅长串联关键词让 Google 给出有用的编码方案。资深开发者甚至造了缩写来揶揄搜不到东西的新人：

- **LMGTFY** — Let me google that for you
- **GIYF** — Google is your friend
- **JFGI** — Just ~~****~~ google it

> 通常不是新人没搜，而是**他们不知道怎么有效地 google**——那是一项磨练出来的技能。

### SQL 的困境

```sql
CREATE TABLE product_descriptions (
    id SERIAL PRIMARY KEY,
    description TEXT NOT NULL
);
```

想找所有 "winter jackets"——真实意图是**所有适合冬天的厚外套**，无论文本里是否出现 winter 或 jacket 这两个词。

```sql
-- 方式 1：字面匹配
SELECT * FROM product_descriptions
WHERE description LIKE '%winter jacket%';

-- 方式 2：全文搜索（MySQL/MariaDB 等）
SELECT * FROM product_descriptions
WHERE MATCH(description) AGAINST('winter jacket' IN NATURAL LANGUAGE MODE);
```

第一个查询靠字面词。第二个好一些，靠词和同义词。**但描述成 "heavy coat for cold weather" 或 "outerwear for frigid climates" 的商品会被漏掉**——仅仅因为文本不匹配 "winter jacket" 或它的近义词。

**向量数据库不同**：它们用 **embedding 模型**捕获自然语言、图像和音频的含义与上下文，创建机器能理解的数字表示——**vector embedding（向量嵌入）**。

> 📌 **已有数据库的向量支持**
>
> 一些关系型和文档数据库（PostgreSQL、MongoDB、Apache Cassandra）已经直接或通过扩展支持向量嵌入。
>
> 例如给 PostgreSQL 加上流行的 **pgvector** 扩展，你就能把向量嵌入作为一种 vector 类型和其余数据存在一起，扩展还提供了执行最近邻和距离相关搜索的 SQL 扩展。
>
> **如果你需要本章描述的相似性搜索能力，先检查你现有数据库方案的能力，再去找专门的向量数据库。**

## 7.3 理解向量嵌入（Vector Embeddings）

> **Embedding 才是 LLM 魔法背后真正的秘密酱料。它们让机器能关联文本、图像和音频。**

**Embedding 模型 = 专门的 AI 模型（神经网络），被训练来把人类理解的数据（文本、图像、音频）转换成压缩的、机器友好的编码——向量嵌入。** 目标是生成一种通用数据表示，让机器能像我们一样理解数据之间的相似性。

```
String                                  →  Embedding
"I'm having password issues.
 Can you help me log in?"               →  [0.01, 0.04, 0.07, ..., 0.05]
```

对我们来说 embedding 就是一个**定长的浮点数数组**。对 AI 模型来说，**这是一个数学向量——高维空间中的一个点**。

### 三维直观理解

想象把知识库文章画在一个（简化的）三维空间里：

- "How to reset your password"
- "Logging in with a password and MFA"
- "Login troubleshooting within your company network"

→ 这三篇**聚在一起**

- "How to change your subscription level"

→ **离得很远**

用户问 "I'm having password issues. Can you help me log in?"，这个问题的点会**靠近登录和密码相关的文章**。这样我们就知道这些文章和用户所问相关。

> **多模态 embedding 模型（multimodal embedding models）** 能处理多种数据类型作为输入：文档、图像、音频都转成向量表示。本书聚焦文本 embedding 模型，但概念是一样的。

### 维度（Dimensions）是什么

**向量嵌入中的每个浮点数代表高维空间中的一个维度。每个维度代表模型被训练来编码的数据的一个特征（feature）。浮点数的值表示被编码的数据与该特征的对齐程度。**

编码结果是一个向量——**这个高维空间中的一个坐标**。我们通过测量两个向量坐标之间的距离来判断两个数据输入有多相似。

### 用水果举例（三维可视化）

假设一个专门描述水果的三维向量空间：

- **Sweetness（甜度，x 轴）**
- **Size（大小，y 轴）**
- **Citrus（柑橘味，z 轴）**

| 水果 | 坐标 | 说明 |
| --- | --- | --- |
| Banana | (8, 7, 0) | 非常甜(8)、中大尺寸(7)、非柑橘(0) |
| Apple | (5, 6, 1) | 中等甜(5)、中等大小(6)、微柑橘(1) |
| Lemon | (2, 4, 8) | 不太甜(2)、较小(4)、强柑橘(8) |

**Banana 和 Apple 靠得更近**（甜度、大小、柑橘味相似），**Lemon 离得远**。

但——**这些特征只适合映射水果。把 Apple（公司）画在这张图上根本没意义。** 幸好真实的向量嵌入远比这复杂。

> ⚠️ **现实中，向量嵌入里的数字对我们没有意义。每个维度捕获模型在训练中学到的某个特征——我们真的不知道这些特征代表什么概念。我们只知道：测量两个向量点之间的距离，就能判断原始数据在上下文上有多相似。**

**一般来说维度越多，模型越准确：**

| Embedding 模型 | 维度（默认/典型） | 说明 |
| --- | --- | --- |
| text-embedding-ada-002 | 1,536 | 仅文本，固定长度 |
| text-embedding-3-small | 1,536（可配置降到 512） | 仅文本。与 Ada-002 同尺寸但准确性更好 |
| text-embedding-3-large | 3,072（可配置到 256 或 1,024） | 仅文本。最高准确性；支持 **matryoshka（套娃）缩放**以加快搜索 |
| clip-ViT-B-32 | 512 | **多模态**（文本或图像）：图像和文本特征同维度 |

> 💡 **多模态的直观例子**：如果你为文本 "apple" 和一张苹果的图片各创建一个 embedding，**两者会被画在彼此附近**——它们只是同一个现实事物的不同表示。

## 7.4 用 Sentence Transformers 生成 Embedding

**Chroma 默认用 Sentence-BERT（SBERT）生成向量嵌入。** SBERT 是 BERT 的一个版本，把**句子**转成向量嵌入。

SBERT 通过 Python 库 **Sentence Transformers**（https://sbert.net）实现和分发，由 AI 社区 **Hugging Face** 维护。

```bash
pip install sentence-transformers==5.1.2
```

**`part3/vector_databases/sentence_transformer.py`**

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")      # ❶

sentences = [                                        # ❷
    "Sony Wireless Noise-Canceling Headphones",
    "Canon Professional DSLR Camera Kit",
    "Jenson Wireless Earbuds Pro",
    "Panasonic Wireless Noise-Reduction Headphones",
]

embeddings = model.encode(sentences)                 # ❸

print(embeddings[0])
print(f"Dimensions: {len(embeddings[0])}")
```

❶ **`all-MiniLM-L6-v2`** 是最常用的 SBERT 模型之一，因为它在**速度、体积和语义性能之间取得了很好的平衡**。

**输出：**

```
[ 9.95301530e-02 4.46034595e-02 2.07065768e-03 -1.21806497e-02
 -6.64805397e-02 2.34791767e-02 -9.21015963e-02 1.09268930e-02
 ... ]
Dimensions: 384
```

### 计算相似度

```python
idx_to_compare = 0

similarities = model.similarity(embeddings[idx_to_compare], embeddings)   # ❶

print(sentences[idx_to_compare])

for idx, embedding in enumerate(embeddings):                              # ❷
    print(f"- {sentences[idx]}, Score: {similarities[idx_to_compare][idx]:.4f}")  # ❸
```

❷ Python 的 `enumerate` 函数让你**同时遍历索引（idx）和元素（embedding）**。
❸ `:.4f` 把相似度格式化为 4 位小数。**相似度分数是 0 到 1 的浮点值，值越高字符串越相似。**

**输出：**

```
Sony Wireless Noise-Canceling Headphones
- Sony Wireless Noise-Canceling Headphones, Score: 1.0000
- Canon Professional DSLR Camera Kit, Score: 0.0892
- Jenson Wireless Earbuds Pro, Score: 0.4783
- Panasonic Wireless Noise-Reduction Headphones, Score: 0.7500
```

- 完全相同 → 最高分 **1.0000**
- 无关商品（DSLR 相机）→ 低分 **0.0892**
- Panasonic 降噪耳机 → 高分 **0.7500**（不同品牌但相似商品）

> 💡 我们不会自己计算向量距离——**让向量数据库替我们做**。但理解底层发生了什么，在结果不符合预期时会很有帮助。

## 7.5 如何选择 Embedding 模型

> **Embedding 模型的选择会显著影响你能得到的结果。它们为特定目的训练和调优，也受训练数据的重度影响（偏见）。不同模型关注的特征可能完全不同。**

| 关键问题 | 考量 |
| --- | --- |
| **你在嵌入什么类型的数据？** | Sentence Transformers 擅长句子/文档相似度等文本任务。**要嵌入图像或音频就需要多模态 embedding 模型** |
| **你处理什么领域？** | 有些模型针对特定领域微调过。**医学术语或法律文档，就考虑在该领域训练过的模型** |
| **你想达成什么？** | 例如做商品推荐，就需要一个能**深度捕获商品描述上下文理解**的模型 |
| **需要哪些语言？** | 需要多语言处理就确保模型支持多语言输入 |
| **性能需求是什么？** | 有些模型为**更快的推理速度**优化。这对实时应用很重要，但可能牺牲准确性 |
| **模型的支持度如何？** | 开放权重模型要确保有好的社区支持、文档和适合你使用场景的许可。商业模型要选来自稳定、资金充足公司的 |
| **模型能否微调？** | 如果你打算微调模型以适配领域特定需求，这是关键考量（Part IV） |
| **成本如何？** | 大模型的 token 成本或算力成本通常更高。**此外 embedding 维度越多，需要的存储越多** |
| **每个 embedding 多少 token？** | LLM 和 embedding 模型都有**请求 token 上限**。第 8 章会展示 **chunking 策略**如何帮你待在限制内 |

### 去哪找模型

- **托管 API**：提供商通常给你几个选择（见上文 OpenAI 表）
- **开放权重**：Hugging Face 的模型搜索（https://huggingface.co/models）。**超过一百万个模型**初看有点吓人，但可以按任务、库、数据集、语言等筛选。找 SBERT 模型就按库 `sentence-transformers` 筛
- **Hugging Face Embedding Leaderboard**：捕获跨语言、任务、领域的对比指标，还有内存占用、最大输入 token 和维度，帮你理解可能的性能和算力指标。**先查排行榜选几个候选，再自己实验**

## 7.6 解读模型名称（Dissecting Model Names）

> **模型名就像 AI 的身份证**，快速告诉你谁创建了它、属于什么家族、多大、经过了什么训练或优化。理解这些用连字符分隔的片段，能帮你选对模型。

### `google/gemma-3-27b-pt`

| 片段 | 含义 |
| --- | --- |
| `google/gemma` | 模型家族是 Gemma，由 Google 开发 |
| `3` | 版本号或模型架构的主要迭代 |
| `27b` | **270 亿参数**。参数是模型内部在训练中被调整的数值；**参数越多通常意味着模型越大越复杂、学习能力越强，但算力需求也越高** |
| `pt` | **Pretrained（预训练）**。在海量数据集上训练以获得通用语言理解和生成能力，**但没有针对特定任务或对话风格做任何微调**。这是原始基座 |

### `google/gemma-3-27b-it`

| 片段 | 含义 |
| --- | --- |
| `it` | **Instruction-tuned（指令微调）**。与 pt 版不同，它经历了额外的训练阶段，专门让它更擅长**遵循指令和进行对话**。为 chatbot 式交互优化。**这通常就是你做聊天机器人或直接下命令时要用的版本** |

### `google/gemma-3-4b-it-qat-q4_0-gguf`

| 片段 | 含义 |
| --- | --- |
| `4b` | 40 亿参数。比 27b 小得多，需要更少内存、跑得更快，**通常适合部署在更普通的硬件上** |
| `it` | 指令微调 |
| `qat` | **Quantization-aware training（量化感知训练）**。模型在训练时就考虑了量化，**学会了对量化过程中的精度降低保持鲁棒**，目标是最小化最终量化后的性能损失 |
| `q4_0` | **4 位量化**，使用某种特定的量化方案。**量化是通过用更少的位（如 4 位而非 16 或 32 位）表示模型数值参数来减小模型体积、加速推理的技术。** 这个版本已经量化过了 |
| `gguf` | **GPT-Generated Unified Format**。一种为高效 CPU（有时 GPU）推理优化的文件格式，**常用于在本地机器上运行 LLM** |

### `distilbert/distilbert-base-uncased-finetuned-sst-2-english`

| 片段 | 含义 |
| --- | --- |
| `distilbert/distilbert` | 模型家族是 **DistilBERT**——BERT 的更小、更快、更轻的版本 |
| `base` | 模型的基础配置（标准尺寸，不是 tiny 或 large） |
| `uncased` | **训练文本忽略大小写差异**（Apple 和 apple 被同等对待） |
| `finetuned` | **关键指示符：模型针对特定下游任务做过微调** |
| `sst-2` | 微调所用的具体数据集：**Stanford Sentiment Treebank v2**，常用于情感分析。**这告诉你该模型很可能擅长判断文本表达正面还是负面情感** |
| `english` | 训练和微调所用的语言 |

### `deepseek-ai/DeepSeek-R1-Distill-Llama-70B`

| 片段 | 含义 |
| --- | --- |
| `deepseek-ai/DeepSeek-R1` | 模型家族是 DeepSeek-R1，由 DeepSeek AI 开发 |
| `Distill` | **知识蒸馏（knowledge distillation）**：训练一个小模型（"学生"）去模仿一个更大更强模型（"教师"）的行为。**目标是用更小更高效的模型获得相近的性能** |
| `Llama-70B` | 通常指明当前模型是从哪个"教师"模型蒸馏来的，或至少指明其血统。**700 亿参数的 Llama 模型很可能就是知识被迁移的那个更大模型** |

> **掌握这些命名技巧意味着你能一眼"读懂"一个模型**——知道它擅长什么、你的电脑跑不跑得动、以及它是否适合你正在构建的项目。

## 7.7 向量数据库检索原理

**向量数据库为存储向量嵌入并高效计算它们之间的距离而专门构建。** 我们可以加载数百万甚至数十亿个代表数据的 embedding，然后用一个问题或陈述查询它，**实时检索最相似的数据**。

### 加载与查询流程

```
第 1 步：为每篇文章生成 embedding 并存入向量库
  "How to reset your password"        → [0.02, 0.04, 0.06, ..., 0.01]
  "Logging in with a password and MFA"
  "Login troubleshooting within your company network"

第 2 步：把用户问题转成 embedding 并查询
  "I'm having password issues. Can you help me log in?"
      → [0.01, 0.03, 0.07, ..., 0.04]
      → Query → 返回最相关的文章

第 3 步：用返回的文章增强 prompt
  Context: Knowledge base articles
    "How to reset your password"
    "Logging in with a password and MFA"
  Question: I'm having password issues. Can you help me log in?
      → LLM
```

**这就是向量数据库对 RAG 方案如此有用的原因**（第 8 章构建完整 RAG）。

### 最近邻算法

**向量数据库用最近邻（Nearest Neighbor, NN）算法通过计算向量嵌入之间的距离来判断相似性。** 查询时它返回 **k-nearest neighbors（k-NN）**，k 是你期望的最近结果数量。

向量数据库通常用 **近似最近邻（Approximate Nearest Neighbor, ANN）** 搜索算法来高效计算这些距离。有多种算法能做到，**它们本质上是用索引和聚类这类聪明的捷径来快速找到结果**。

> ⚠️ **ANN 的捷径意味着搜索结果会非常接近，但不保证精确。** 选择向量数据库方案时记住这个"效率优先于绝对正确性"的权衡。

> 📌 **ENN vs ANN**
>
> **精确最近邻（ENN）** 向量搜索计算所有已索引向量的所有距离，因此基于距离度量**保证检索到最近的邻居**——结果保证准确。
>
> 虽然一些向量数据库支持 ENN，但**对大量向量嵌入而言效率极低**，只应在嵌入数量少且精度极其重要时考虑。**ANN 搜索算法足够高效，能在高维向量空间和数百万甚至数十亿嵌入的情况下实时使用。**

## 7.8 实战一：语义搜索

> 对应代码：`part3/vector_databases/product_search_simple.py`

**脚本要做的事：**

1. 从数据源检索所有商品
2. 初始化 embedding provider（用 `all-MiniLM-L6-v2`）
3. 创建使用该 embedding provider 的向量数据库客户端
4. 为每个商品创建用于生成 embedding 的描述性文本
5. 把所有商品连同商品属性作为**元数据**加入向量数据库以便索引

### 创建 Collection

> **在 Chroma 里，collection 是你操作的主容器**——一个具名的文档（或其他记录）分组，包含它们的 embedding（向量）和一起存储的任何元数据。

```bash
pip install chromadb==1.2.1 pandas==2.3.3 numpy==1.26.4
```

| 库 | 作用 |
| --- | --- |
| `chromadb` | 提供 Chroma 接口 |
| `pandas` | 数据分析与操作库 |
| `numpy` | Python 数值计算核心库 |

```python
import chromadb
from chromadb.utils import embedding_functions

client = chromadb.Client()

embedding_function = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="all-MiniLM-L6-v2"
)

collection = client.create_collection(
    name="product_search",
    embedding_function=embedding_function
)
```

> **Collection 会替我们处理 embedding 生成——我们只需要告诉它用哪个 embedding 模型。**
>
> Chroma 在 `embedding_functions` 包中提供了对流行 embedding provider 的封装。**找不到你要的？可以实现 `EmbeddingFunction` 协议自己造一个。这是向量数据库的常见模式**，让你选择最适合需求的 embedding 模型。

> 💡 **这个 Chroma 数据库存在哪？** 为简单起见我们用的是 Chroma 的 **ephemeral client（临时客户端）**，跑一个内存服务器——**程序退出所有数据就消失**。需要持久化就切换到 persistent client 或以 client-server 模式运行 Chroma。本书统一用临时设置保持示例轻量，你可以自己试试持久化选项。

### 准备文本并插入

商品 CSV 长这样：

```csv
product_id,title,category,description,price
E001,4K Ultra HD Smart LED TV 55-inch,Electronics,"Experience stunning visual...",799.99
E002,Wireless Noise-Canceling Headphones,Electronics,"Immerse yourself in pure audio...",349.99
E003,Professional DSLR Camera Kit,Electronics,"Capture life's precious moments...",1499.99
```

**`title` 和 `description` 列捕获了我们需要的上下文。** 加载向量库前要把这两列合成每个商品的单段文本：

```python
import pandas as pd

products_df = pd.read_csv('products.csv')                    # ❶

all_titles = products_df['title']                            # ❷
all_descriptions = products_df['description']                # ❸

all_titles_and_descriptions = zip(all_titles, all_descriptions)   # ❹

texts = [ f"{title} {desc}" for title, desc in all_titles_and_descriptions ]   # ❺
```

❶ `read_csv` 把 CSV 加载成 **DataFrame** 对象，可以按表头引用每一列。
❷❸ `products_df['title']` 返回一个可迭代的 **Series**。
❹ `zip` 把标题和描述合成一个可迭代对象。
❺ 这行用了**内联推导式（inline comprehension）**——本质就是一个方便地遍历 `all_titles_and_descriptions` 的内联 for 循环。**这是常见的 Python 惯用法。**

> 💡 **思考题**：embedding 模型的 token 限制比 LLM 小得多。**如果标题和描述的大小超过了 embedding 模型的最大输入怎么办？** 想想有哪些缩减文本大小的选项，自己试试。

```python
collection.add(
    documents=texts,
    metadatas=[{                                    # ❶ 元数据
        'product_id': pid,
        'title': title,
        'category': category,
        'price': price,
    } for pid, title, category, price in zip(
        products_df['product_id'],
        products_df['title'],
        products_df['category'],
        products_df['price']
    )],
    ids=[pid for pid in products_df['product_id']]  # ❷ 唯一 ID
)
```

❶ **元数据让我们能检索嵌入文档的有用信息**，用于进一步过滤、额外查询或直接使用数据。
❷ 必须为 embedding 提供 id 列表——这里用每个商品唯一的 `product_id`。

> 📌 **向量数据库的 CRUD 操作**
>
> 和你熟悉的数据库一样，向量数据库支持增删改查。Chroma 提供的 collection API：
>
> | API | 作用 |
> | --- | --- |
> | `add` | 向 collection 添加新记录 |
> | `update` | 按 ID 更新记录 |
> | `upsert` | 按 ID 更新记录，找不到就创建 |
> | `delete` | 从 collection 移除记录 |
>
> 也有添加、获取、删除 collection 本身的 API。

## 7.9 实战二：推荐引擎

> 对应代码：`part3/vector_databases/product_recommender.py`、`product_recommender_with_filter.py`

**每个 embedding 都捕获了商品的语义理解**，所以给定商品的标题和描述，我们就能用向量库找到其他相关商品。

**电商场景的用例：**

| 用例 | 说明 |
| --- | --- |
| **推荐相关商品** | 展示某商品时，展示其他相关商品让用户比较或被诱导追加购买 |
| **基于购买历史推荐** | 知道用户购买历史，就能用他们买过的商品找到可能感兴趣的相似商品 |
| **给新商品分类** | 按类别过滤商品很常见（服装、电子、家居）。**用户新增商品时，我们可以找相似商品来推荐合适的类别** |

### 为什么用向量库而不是训练 ML 模型

| 优势 | 说明 |
| --- | --- |
| **简单性（Simplicity）** | 不用训练 ML 模型，用预训练 embedding 模型即可 |
| **可解释性（Interpretability）** | 我们能确切看到哪些现有商品与过往购买最相似 |
| **灵活性（Flexibility）** | 系统能轻松处理新商品和新类别**而无需重新训练** |
| **相关性打分（Relevance scoring）** | 相关性分数基于相似度和商品类别 |

### 定义数据类

```python
from dataclasses import dataclass, field
from typing import List

@dataclass                                                # ❶
class Product:
    product_id: str
    title: str
    category: str
    description: str
    price: float

    def title_and_description(self) -> List[str]:         # ❷
        return f"{self.title} {self.description}"

@dataclass
class PurchaseHistory:
    products: List[Product] = field(default_factory=list)  # ❸

    def has_purchased_product(self, product_id: str) -> bool:      # ❹
        return any(product.product_id == product_id for product in self.products)

    def get_purchase_descriptions(self) -> List[str]:              # ❺
        return [product.title_and_description() for product in self.products]

@dataclass
class User:
    username: str
    purchase_history: PurchaseHistory = field(default_factory=PurchaseHistory)  # ❻
```

❶ **`@dataclass` 注解**——之前我们用 Pydantic 定义代表 schema 的类。**用这个注解定义的类是简单的数据类：主要用于存储数据，不继承或实现任何框架特定的类或接口。**

**它自动生成这些特殊方法：**

| 方法 | 作用 |
| --- | --- |
| `__init__` | 对象构造器 |
| `__repr__` | 魔术方法，返回对象的官方字符串表示 |
| `__eq__` | 魔术方法，判断对象相等性（Python 用 `==` 比较对象时使用） |

**这减少了样板代码。** 例如 `Product` 自动获得：

```python
def __init__(self, product_id: str, title: str, category: str,
             description: str, price: float):
    self.product_id = product_id
    self.title = title
    self.category = category
    self.description = description
    self.price = price
```

❸❻ 用 `field` 方法定义 `default_factory`，**确保这些属性在对象创建时总是被初始化为默认值。**

### 检索推荐

```python
"""
Get product recommendations based on purchase history

Args:
  purchase_history: The user's PurchaseHistory
  n_recommendations: Number of recommendations to return
  same_category_weight: Weight given to products in the same category

Returns:
  List of recommended Product objects
"""
def get_recommendations(self,
                        purchase_history: PurchaseHistory,
                        n_recommendations: int = 3,
                        same_category_weight: float = 0.7) -> List[Product]:
    if not purchase_history.products:
        return []

    # Use our method to get the purchased product titles and descriptions
    purchased_descriptions = purchase_history.get_purchase_descriptions()   # ❶

    # Get recommendations based on description similarity
    results = self.collection.query(
        query_texts=purchased_descriptions,                                 # ❷
        # Get extra results to account for filtering
        n_results=n_recommendations + len(purchase_history)                 # ❸
    )
```

❸ **注意加上了购买历史的长度！** 因为**用户购买历史中的商品会是最相似的结果**——我们要事后把它们过滤掉。

`same_category_weight` 让我们给与过往购买同类别的结果**更高优先级**，通过查看元数据里的 `category` 值判断。

### 计算相关性并重排序

```python
recommendations = []

for idx, metadata in enumerate(results['metadatas'][0]):     # ❶
    product_id = metadata['product_id']                       # ❷

    # Skip if this product was already purchased
    if purchase_history.has_purchased_product(product_id):    # ❸
        continue

    # Calculate category bonus
    category_bonus = same_category_weight if any(             # ❹
        p.category == metadata['category'] for p in purchase_history.products
    ) else 0

    product = self.find_product(product_id)                   # ❺
    product.relevance_score = results['distances'][0][idx] + category_bonus   # ❻
    recommendations.append(product)

    if len(recommendations) >= n_recommendations:
        break

# Sort by relevance score (lower is better)
recommendations.sort(key=lambda x: x.relevance_score)         # ❼

return recommendations
```

❸ 排除用户已购买的商品。
❹ 给与用户过往购买同类别的商品加分——**这是一种收窄到用户可能感兴趣商品的策略**。
❻ `relevance_score` = **Chroma 计算的距离 + 类别加成**。
❼ 排序，最相关的在前。**这是一种结果重排序（re-ranking）** —— 第 8 章讲更高级的 RAG 主题时会深入。

> 📌 **向量数据库的距离计算**
>
> **Chroma 默认的距离计算是 L2（欧氏）距离**——高维空间中两点之间的直线距离。
>
> 另外两种支持的计算方式，想象从图原点画一条线到向量嵌入点：
> - **cosine（余弦）距离**：优先考虑这条线的**方向**
> - **ip（inner product，内积）**：同时优先考虑向量的**方向和长度**
>
> 创建 collection 时通过 `hnsw:space` 元数据选项设置：
>
> ```python
> collection = client.create_collection(
>     name="products",
>     embedding_function=embedding_function,
>     metadata={"hnsw:space": "cosine"}
> )
> ```
>
> ⚠️ **这个选项影响 collection 的创建方式，所以和 `embedding_function` 一样，只能在创建 collection 时设置。**

### 元数据过滤

> 到目前为止我们的推荐完全基于 embedding 之间的相似度。**但这只是故事的一部分——真实的推荐往往需要考虑关于用户的额外上下文。**
>
> 如果我们捕获了用户信息（年龄段、位置等人口统计数据，或购物偏好），推荐能更贴切。**比如我们大概不想给住在市中心、从不买户外装备的人推荐登山靴。**

**`part3/vector_databases/product_recommender_with_filter.py`**

```python
purchase_categories = [                                     # ❶
    product.category for product in purchase_history.products ]

# Get recommendations based on description similarity and category metadata
results = self.collection.query(
    query_texts=purchase_history.get_purchase_descriptions(),
    n_results=n_recommendations,
    where={"category": {"$in": purchase_categories}}        # ❷
)
```

> **元数据过滤器工作起来很像 SQL 查询**：让你基于元数据条件而非仅向量相似度来收窄结果。你可以组合多个条件、比较值，甚至按范围或列表过滤。

**`where` 过滤器支持的操作：**

| 类型 | 操作符 | 示例 |
| --- | --- | --- |
| **逻辑操作符** | `$and`, `$or` | 组合多个条件（electronics 类别 **且** 低于 $100） |
| **比较操作符** | `$eq`, `$gt`, `$lt` | 直接比较数值或文本 |
| **集合操作符** | `$in`, `$nin` | 匹配多个可能值之一（categories in [books, games]） |

> 💡 也可以用 `where_document` 过滤器**按文档内容**过滤。
