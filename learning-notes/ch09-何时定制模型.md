# 第 9 章 · 为什么以及何时定制模型

> Part IV 开篇。本章无代码，是微调（fine-tuning）的决策框架。

## 📖 场景引入：收件箱问题（The Inbox Problem）

创业团队成功实现了 AI 客服 agent，RAG 方案在网站上效果惊人，第一次跑在了工单队列前面。

受此鼓舞，他们扩展了 agent：**为什么不直接按主题和严重性给收到的支持邮件分类呢？** 初期效果不错。

**但把 agent 扩展到邮件端打开了一个意外的闸门。** 落进收件箱的不只是支持请求了：

- 销售询价（"Tell me about your enterprise plan..."）
- 合作提案（"We think our companies could collaborate on..."）
- 媒体请求（"Would you be available for an interview about your viral launch?"）
- 以及无穷无尽的垃圾邮件（"Boost your SEO with..."）

**典型的周一现在积压 1,200 条 agent 处理不了的消息**，工程师不得不周末加班仅仅为了分诊收件箱。

> **更大的问题不是回答它们，而是理解它们是什么。** 这是热门线索还是又一个垃圾邮件？这是关键的支持问题还是供应商推销？

他们急需的是一个**智能的收发室文员**：看每一封邮件并立刻贴上标签——**不是泛泛的标签，而是针对这家公司需求的具体标签**：Sales Lead、Customer Support、Partnership Idea，或者干脆 Junk: Ignore。不符合任何关键类别的要另放一边标为 Unread 供人工审查。

> **现有系统在检索信息和生成响应上再强大，也不具备对这家企业所拥有的对话类型的天生理解。它了解产品，但不知道如何基于销售推销、支持工单、真诚媒体询问所使用语言的细微差别来分类邮件背后的意图。**

**这条路就是微调（fine-tuning）。**

### 关于数据集的关键提醒

要微调一个模型准确执行这项任务，**首先需要一个由大量示例邮件组成的数据集，每封都正确标注了它所属的类别**。

**挑战在于获得一个真正代表你的 AI agent 将遇到的邮件的多样性和细微差别的数据集。**

> ⚠️ **虽然可以用强大的 LLM 生成合成（虚构）邮件，但只依赖这种方法有潜在缺点。**
>
> 如果你的目标是微调一个在真实世界、未见过的邮件上表现得和 Google/OpenAI 的大型商业模型一样好甚至更好的模型，**只用那些同样的模型生成的数据来训练，可能无法真正测试它在新颖示例上的能力**。你微调的模型可能非常擅长分类与合成邮件相似的邮件，**但它在从未见过的真实邮件上的表现会是不确定的**。

**实用可靠的数据集，最好的资源往往是反映实际任务的真实数据——在这个案例中，就是你自己的邮件。** 别担心，书中会给出在你自己的系统上安全私密地处理数据的步骤——**微调过程中你的邮件不会被发送到外部服务**。

## 9.1 预训练模型的边界

当你通过 Ollama 或 Hugging Face 使用模型，或与 ChatGPT/Gemini 交互时，**你在与预训练模型交互**。预训练模型从某人或某团队提供给它的一组数据中"获得"了技能。**这类通用预训练模型省时省力，因为我们不必从零构建基础模型。**

### 什么时候不需要微调

| 场景 | 推荐方案 |
| --- | --- |
| 询问广为人知的信息、生成创意文本、总结通用话题、翻译、以 LLM 标准能力内的不同风格改写内容 | **仅用提示工程**通常就能取得优秀结果 |
| 需要 LLM 基于**不在其原始训练数据中的信息**回答问题或生成内容——近期新闻、你组织特有的文档、某份报告的细节 | **RAG 是理想方案** |

### 什么时候需要微调

> 想象你在一个非常专业的行业工作，比如制造业，**内部报告遵循高度特定的模板、大量使用专有术语、要求数据以独特的结构化格式呈现。**
>
> 你想用 AI 基于原始输入数据自动生成报告草稿。虽然基座 LLM 能理解和生成语言，RAG 能帮它访问特定数据点，**但预训练模型难以持续地应用那些精确的内部格式规则、在上下文中正确使用专有术语、并维持那种与其通用训练数据显著偏离的结构。**
>
> **提示能帮上一定的忙，但要在这个狭窄的技术细分领域内实现真正的一致性和准确性，基座模型的通用训练是不够的。**

**面对这种情况，你有两条路：**

1. **从零构建新模型**
2. **微调预训练模型**

---

## 9.2 从零构建 vs 微调

### 从零构建新模型

```
海量数据（主要来自互联网）
     ↓
  数据准备
     ↓
   数据集
     ↓
   训练 ←──┐
     ↓     │ 重复
   验证 ───┘
     ↓
   发布
     ↓
  新模型

⏱ 耗费大量时间和精力
```

**提供完全的控制和定制，但需要海量数据、算力资源和专业知识。**

### 微调预训练模型

```
        小规模原始数据
             ↓
          数据准备
             ↓
           数据集
             ↓
   预训练模型 → 微调 ←──┐
             ↓          │ 重复
           验证 ─────────┘
             ↓
           发布
             ↓
          新模型

⏱ 只需一小部分时间和成本
```

**利用已有知识实现更快的训练和更好的性能，所需数据更少，但控制力较弱，且可能携带原始训练数据的偏见。**

> 📌 **AI 中的 bias（偏见）** 指模型产生持续扭曲的结果或不公平偏见时发生的**系统性错误**。它通常源于反映了人类刻板印象、历史不平等或非代表性样本的训练数据，导致输出被扭曲。

### 优劣对比

| | ✅ 优点 | ❌ 缺点 |
| --- | --- | --- |
| **从零构建新模型** | **完全控制**：对模型架构、设置和训练过程有完全控制<br>**定制化**：可以精确地为你的特定任务和数据量身定制<br>**无依赖**：不依赖任何预训练模型或外部资源 | **需要海量数据**：从零训练通常需要大量标注数据<br>**计算成本高**：训练耗时且资源密集<br>**需要专业知识**：设计和训练新模型需要大量 ML 专业能力 |
| **微调预训练模型** | **利用已有知识**：从一个已经学会通用语言模式和表示的模型开始<br>**数据高效**：特定任务所需的标注数据显著更少<br>**训练更快**：通常比从零训练快<br>**更易实现**：往往比构建新模型简单 | **控制力较弱**：对模型架构和初始参数控制较少<br>**可能有偏见**：预训练模型可能携带其原始训练数据的偏见<br>**可能不是最优**：对独特或高度专业的任务，微调未必总是最佳方案 |

### 决策清单

**从零构建新模型，当你有：**

- 一个有独特要求的非常特定的任务
- **海量的标注数据**
- 进行广泛模型开发的专业知识和资源

**微调预训练模型，当你有：**

- **针对特定任务的有限标注数据**
- 想利用已有知识并实现更快训练的意愿
- **一个与预训练模型已训练任务相对相似的任务**

> 💡 **微调的另一个优势：我们可以拿一个参数相对较少的小模型，让它真正表现出色。有时候，一个参数量更低的微调模型能超越一个拥有数十亿参数的通用模型。**

## 9.3 三种微调策略（Strategies）

**三种主要策略，区别在于数据如何标注、模型如何从反馈中学习。**

### 1. Self-Supervised Fine-Tuning（自监督微调）—— 从模式中学习

> 想象教一个孩子：给他一个庞大的图书馆，让他猜他读的每本书里的下一个词。**这就是自监督学习的本质——正是用来训练我们今天使用的基础语言模型的方法。** 模型通过识别海量文本中的模式和关系来学习，本质上是预测接下来是什么。

**用于微调时，这种方法允许高度定制。通过仔细选择模型学习的文本，你可以为特定任务或风格量身定制它。**

例如，**如果你想让语言模型模仿你独特的写作声音，可以用你自己的作品集来微调它**，让模型吸收并复现你风格中的微妙之处，使其输出极其个性化。

### 2. Supervised Fine-Tuning（监督微调）—— 从示例中学习

> 更直接的方法，**类似于用抽认卡（flashcards）教学**。模型从一个把每条信息与对应标签或答案配对的数据集中学习。

**把这个策略想成给模型提供清晰的输入和期望输出的示例。**

例如想改善模型回答问题的能力，可以用**问答对数据集**微调它。模型学会把特定问题与其正确答案关联起来，提升准确性和响应能力。

> **这是存在清晰输入-输出关系的任务的强大技巧，允许对模型行为进行精确控制。**（本书示例采用的就是这种）

### 3. Reinforcement Learning Fine-Tuning（强化学习微调）—— 从反馈中学习

> 引入一个**反馈循环**，类似于老师引导学生进行迭代修改。**训练一个独立的"奖励模型（reward model）"来评估语言模型输出的质量**，这个奖励模型提供反馈，本质上给模型的响应排名，引导它产生更好的结果。

**OpenAI 用这种方法开发了 InstructGPT。人类标注员给模型输出打分，这些评分被用来训练奖励模型。**

> **通过纳入人类的偏好和判断，强化学习允许微调与复杂、主观的标准对齐，产生更细致、更理想的输出。**

## 9.4 两种微调方法（Methods）

**方法主要区别在于所需的技术细节和编码量。**

### No-Code Fine-Tuning（无代码微调）

> **迈入微调不一定需要立刻具备 ML 代码和基础设施的深厚专长。** 无代码方法通过提供专门工具（通常带直观的图形界面）大幅简化了流程，**抽象掉了搭建训练环境、管理硬件、编写训练循环的底层复杂性**，让你能更直接地关注数据和模型的期望结果。

**Hugging Face AutoTrain**（https://huggingface.co/docs/autotrain/index）

- 可作为在线托管工作区访问，也可下载在自己机器上运行
- 你只需：**上传准备好的训练和验证数据集文件 → 从列表中选择要微调的基座模型 → 通过点选或简单表单配置关键训练参数**
- AutoTrain 在后台处理繁重的训练工作

**也提供 CLI 方式：**

```bash
autotrain text-classification \
--train \
--model distilbert/distilbert-base-uncased \
--project-name my-mail-classifier \
--data-path data/ \
--train-split train \
--valid-split valid \
--text-column text \
--target-column label \
--epochs 3 \
--batch-size 4 \
--lr 2e-5 \
--optimizer adamw_torch \
--scheduler linear \
--gradient-accumulation 1 \
--mixed-precision fp16
```

> ⚠️ **虽然 CLI 是启动实验的绝佳捷径，但它往往充当一个"黑盒"，隐藏内部逻辑并限制你调整细节的能力。**

### Technical Fine-Tuning（技术性/代码微调）

**提供对整个过程显著更多的控制**：精确管理数据准备、配置详细的训练参数、对模型训练的底层机制获得更深的理解。

> ⚠️ **但这种增加的控制和灵活性需要更大的时间投入**来学习相关概念并编写构建和管理微调流水线的代码。

**本书将用 Hugging Face 库演示（第 11 章深入）：**

| 主题 | 内容 |
| --- | --- |
| **准备数据集** | 学习如何用代码正确加载、处理和格式化数据用于模型训练，理解创建健壮数据集的重要考量 |
| **微调标准分类模型** | 用 **DistilBERT** 这样的模型作为具体、更简单的例子，说明为特定文本分类任务训练模型的基本步骤 |
| **微调 LLM** | 探索微调 LLM 与微调更小的分类模型有何显著不同，理解高级 LLM 定制所用的特定数据类型和技术 |

> 💡 **值得关注的工具**：虽然核心库很强大，但你常会想用专门为**快速和内存高效微调**构建的开源工具。**这是 AI 中快速演进的领域，新工具不断出现。** 这些工具被巧妙设计来大幅降低定制模型对计算机内存的要求。一个流行的例子是 **Unsloth**（https://unsloth.ai），旨在让微调极快。**这类工具值得探索，它们能显著降低你项目的硬件门槛。**

## 9.5 微调的三大步骤

**无论采用哪种方法，训练过程都有三个主要步骤**（不仅适用于微调，也适用于构建你自己的模型）：

1. **准备数据（Prepare the data）** ← 第 10 章
2. **微调模型（Fine-tune the model）** ← 第 11 章
3. **测试新模型（Test the new model）** ← 第 11 章

**就这样。三个简单步骤。**

---

## 本章小结

- 通用模型即使配上提示工程或 RAG，在有独特要求的高度特定任务上也会力有不逮
- **从零构建 vs 微调**的权衡：控制力 vs 效率
- **微调的独特优势**：利用已有知识、减少数据需求；**微调过的小模型甚至能超越更大的通用模型**
- **三种策略**：自监督（从模式学）、监督（从示例学）、强化学习（从反馈学）
- **两种方法**：无代码（AutoTrain）、技术性（Hugging Face 库）
- **三大步骤**：准备数据 → 微调 → 测试
