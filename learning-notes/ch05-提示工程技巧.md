# 第 5 章 · 提示工程技巧（Prompt Engineering Techniques）

> 这仍是一个**开放的研究领域**，不同模型偏好的方法可能不同。本章是作者在实践中最有用的一批技巧。

## 学习建议

1. **亲手试每个示例**。用第 3 章的示例，或者 Ollama 聊天会话、ChatGPT、Gemini 都行。试着**组合多种技巧**，观察对响应的影响。
2. **想想同样的任务用传统编码怎么做**。当你想象靠模式匹配实现的复杂度时，你会立刻意识到 LLM 方案的价值。

## 5.1 指令提示（Instruction Prompting）

> **LLM 的好坏取决于我们给它的指令。** 给对 prompt，它能做从文本重排、数据抽取、去除个人身份信息（PII）到文本分类的一切——**不需要庞大的标注数据集，也不需要嵌在代码里的脆弱规则。**

### 用例 1：数据抽取（Data Extraction）

LLM 能识别文本中**语义上有意义的部分**——姓名、职位、地点、日期、金额、ID 等，即使措辞千变万化。这让它成为从 PDF、Word 文档、邮件线程、社媒帖子等非结构化来源抽取数据的强大工具。

相比**格式一变就崩溃的正则表达式**，LLM 能从上下文泛化：

- "Sarah Whitfield, Director of Customer Experience" → 既是姓名也是职位
- "$1,565 due by 12/1/2025" → 包含金额和日期
- "Suite 400, 123 Main St., Austin, TX 78701" → 是地址

**即使这些字段没有标签，LLM 也能理解文本背后的含义。**

> 📊 据估计，企业数据的 **80–90% 是非结构化的**。也就是说，你的组织几乎肯定坐拥大量锁在文档、收件箱和知识库中的有价值事实。基于 LLM 的抽取能把这些数据变成可存储、可搜索、可分析的结构化记录：
> - 支持工单元数据
> - 邮件中的客户联系人
> - 合同中的关键条款
> - 发票中的 SKU

**示例 prompt：**

```
Given the following email:

Hi Jacob,

Thank you for sending over the detailed proposal. I've reviewed it with our
product and customer success leads, and we're excited about the project.

Please put together an SOW for review so we can get things started. We'd like
you to travel to our office in Denver, Colorado, for the kick off meeting.

Thanks again for the thorough proposal. I'm looking forward to collaborating.

Best regards,

Sarah Whitfield
Director of Customer Experience
Acme Software Solutions
sarah.whitfield@acmesoft.com · (312) 555-0182

Extract the sender's name, location, and job_title, company, email, and
phone_number. Provide the results back in JSON format where each data element
is an attribute. Only return the JSON in your response.
```

**响应**（Llama 3.2 3B）：

```json
{"sender_name": "Sarah Whitfield", "location": "Denver, Colorado",
 "job_title": "Director of Customer Experience", "company": "Acme Software
 Solutions", "email": "sarah.whitfield@acmesoft.com", "phone_number":
 "(312) 555-0182"}
```

**观察要点：**

- LLM 只用最少指令就从签名档里提取了 Sarah 的联系方式
- 它还**从邮件内容推断出** Sarah 在 Denver, Colorado 办公室
- **LLM 接住了我们给的属性命名暗示**：prompt 里 `job_title` 和 `phone_number` 用了下划线，输出就照做了

⚠️ **但这不够好**：对一次性自用的 prompt 够用，但**无法保证代码需要的一致 JSON 格式**。第 6 章会用**结构化输出**大幅改进。

⚠️ **另一个隐患**：Sarah 其实没说她的位置——**LLM 在做假设！** 取决于你的用例，你可能需要更具体的指令、要抽取字段的描述、和/或示例来确保响应正确。

### 用例 2：PII 移除

保护 PII 对组织很重要，很多时候还是法律要求。这通常意味着必须**脱敏（redact）**，除非数据以极其安全的加密方式存储。

> ⚠️ **重要警告：LLM 使用中的数据隐私与安全**
>
> 在把含敏感信息（PII 是最敏感的一类）的 prompt 发给 LLM 之前，你需要清楚这些数据的**生命周期**：
> - 用**托管 API**：搞清托管公司如何保护你 prompt 中的数据，以及**你的 prompt 数据是否会被用于模型训练**
> - 用**自托管 LLM**：确保你没有以可能暴露隐私信息的方式记录或保留 prompt

非结构化文本（如客服聊天记录）很难做 PII 清洗。正则和其他解析技术能移除已知模式（如社保号），但**常常漏掉边缘情况和格式变体**。LLM 能用语义理解补足这些规则，识别模式匹配会漏掉的**语义等价的 PII**。

```
Given the following customer chat, redact any personally identifiable
information (PII) and replace it with a placeholder (for example, [name]).
Redact the following data: name, phone number, email, and address.

<chat>
Agent: Hi Jacob, welcome to Customer First Bank. How can I help you today?
Customer: I need to order new checks.
Agent: Sure, I can help you with that. Can you verify a few things for me?
I need your phone number and your address.
Customer: Sure. My phone number is 214-555-1234 and my address is 1234 Fake
St, Dallas, TX 75002.
Agent: Perfect. I've ordered you a new set of checks that will be shipped to
your address. You will receive a confirmation email at:
jacob.orshalick@email.com.
Customer: Thanks!
</chat>

Only return the <chat> content with the PII redacted.
```

**响应：**

```
<chat>
Agent: Hi [name], welcome to Customer First Bank. How can I help you today?
Customer: I need to order new checks.
Agent: Sure, I can help you with that. Can you verify a few things for me? I need your phone number and your address.
Customer: Sure. My phone number is [phone number] and my address is [address].
Agent: Perfect. I've ordered you a new set of checks that will be shipped to your address. You will receive a confirmation email at: [email].
Customer: Thanks!
</chat>
```

**两个技巧：**

1. **LLM 从一个示例 `[name]` 就隐式理解了占位符格式**
2. 用 XML `<chat>` **分隔符**标出聊天内容的起止——分隔符是帮 LLM 识别 prompt 中特定内容的好办法

### 用例 3：合成数据生成（Synthetic Data Generation）

LLM 非常适合生成用于测试或示例的合成数据，格式可以是 JSON、XML、CSV、SQL INSERT 语句等。适用场景：

- 开发、测试或演示环境
- 单元测试或集成测试
- 负载测试场景
- **不用生产数据就能复现缺陷场景**

**示例（生成第 7 章向量数据库用的商品数据）：**

```
Generate a CSV file containing 30 rows of random product data. The CSV should
have the following headers and columns, in this exact order:

- product_id
- title
- category
- description
- price

The first row must be the header. Each subsequent row should represent a
unique product with a random but plausible value for each column:

- product_id: A unique alphanumeric code (for example, E001 A002, etc).
- title: A realistic product name.
- category: Either "Electronics" or "Apparel".
- description: A detailed, natural-sounding product description (2-5 sentences).
- price: A realistic price as a decimal (for example, 199.99).

The total number of rows (including the header) should be 31. Do not repeat
any product_id. The output should be valid CSV format, with all fields
properly quoted if necessary.

Example header:
product_id,title,category,description,price

Begin generating the CSV below this line:
```

> 💡 这个 prompt 是用 **Cursor（Agentic 模式 + Claude 3.5 Sonnet）** 跑的。任何 LLM 都能跑，但**AI 编码助手的好处是能把 products.csv 直接生成到你的项目里**，你还能继续让它写摄取和使用这些数据的代码。
>
> 成品见 `part3/vector_databases/products.csv`。

## 5.2 角色提示（Persona Prompting）

**Persona 是给 LLM 一个虚构角色身份的提示技巧**，指示它以那个人的身份来响应和行动。

**实验**：问 "Can you tell me how to authenticate to Gmail?"，"authenticate" 这个词在不同语境下含义不同。

### Persona 1: 软件开发者

> **Prompt**: `You are a software developer. Can you tell me how to authenticate to Gmail?`
>
> **Response**: 作为软件开发者，我可以指导你用 **OAuth 2.0** 认证 Gmail……
> **前置条件**：1. 有 Gmail 账号 2. 在 Google Cloud Console 注册了 client ID 3. 装了对应语言的依赖（如 Google API Client Library for Python）
> **Step 1: Register Your Application** ...

模型聚焦在**开发者视角的认证方法**——"authentication" 意味着我们大概率想访问一个安全的 API。

### Persona 2: Google 客服代表

> **Prompt**: `You are a Google help desk representative. Can you tell me how to authenticate to Gmail?`
>
> **Response**: 您好！很乐意帮您认证 Gmail 账号。
> **方法 1：使用网页浏览器** 1. 在浏览器打开 Gmail 登录页 2. 输入 Gmail 地址和密码 3. 点击 "Next" ...

模型转向**帮用户登录 Gmail 网站**——作为客服代表，它意识到用户可能收到了"认证失败"提示，正想知道下一步该怎么办。

### Persona 的好处

**Persona 基于模型的预训练提供了隐式指令**，好处包括：

| 好处 | 说明 |
| --- | --- |
| **更紧的任务框定** | 减少需要的显式指令量，简化 prompt |
| **降低成本** | prompt 越小，收费的 token 越少 |
| **响应一致性** | 固定 persona 保证长对话中语气和风格一致 |
| **响应安全性** | 专业身份有助于限定领域范围、减少危险输出（第 6 章 guardrails 详述） |

可以是医生、会计、乐评人、软件工程师。甚至可以很专：
> "You are an accounting software integration engineer with extensive experience integrating QuickBooks APIs."

> ⚠️ **警告**：使用**医生、律师、财务顾问**这类专业 persona 时要格外小心。这些角色暗示了受监管领域的专业能力，**如果模型的响应被误认为专业建议，可能带来法律或伦理后果**。务必明确说明 AI 不是持证专家，其响应仅供参考。

## 5.3 Zero-shot / One-shot / Few-shot 提示

**通过示例教学（teach-by-example）是一种上下文内学习（in-context learning）。LLM 是 zero-shot、one-shot 和 few-shot 学习者。**

| 类型 | 定义 |
| --- | --- |
| **Zero-shot** | 只给恰当的指令，依赖模型的预训练生成响应 |
| **One-shot** | 在 prompt 中给**一个**示例，教模型如何响应指令 |
| **Few-shot** | 在 prompt 中给**多个**示例，教模型在各种场景下如何响应 |

### 从 zero-shot 到 few-shot：情感分析

**Zero-shot（第 4 章的版本）：**

> **Prompt**: `Tell me if the following statement is positive, neutral, or negative: Thank you @AcmeCorp! Can't wait to try this new shampoo! Sentiment:`
>
> **Response**: `Sentiment: Positive`

模型的预训练足以判断情感，但**我们对"想要什么形式的响应"给的指令太有限**。它可能回 `Sentiment: Positive`、`Positive` 或 `The statement is positive`——**技术上都对**。

**Few-shot 版本：**

```
<instructions>
You are an expert on sentiment analysis. You will analyze a statement and
respond with the sentiment as positive, negative, or neutral.
</instructions>

<examples>
User: Thank you @AcmeCorp! This new shampoo has been great!
Assistant: positive

User: My order from @AcmeCorp never arrived and customer service wasn't
helpful.
Assistant: negative

User: I wouldn't trust @AcmeCorp.
Assistant: negative
</examples>

User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great.
Assistant:
```

**响应**：`positive` ✅

**根据我们提供的示例，模型知道我们只想要小写的 `positive`。** 注意我们用了通用角色 **User** 和 **Assistant** 来描述示例——下一章你会看到，**从代码直接调 API 时角色特别有用**。

> 💡 用预训练模型做分类时，准确性由这两点驱动：
> 1. **模型是怎么训练的**
> 2. **示例的数量和多样性**
>
> 这里模型本来就懂"情感"这个概念，示例只是在指示它**我们想要什么样的响应形式**。

### 进阶：分类到内部知识（部门路由）

场景：识别一条社媒评论该路由到哪个部门，好把负面评论自动开工单发给对的部门。

**公司的部门是内部知识，LLM 没被训练过。没关系——这是分类问题，few-shot 能搞定：**

```
<instructions>
You are an online customer feedback expert.
Analyze the provided statement carefully and respond with the sentiment as
positive, negative, or neutral.
Specify the department the statement should be routed to:

- customer_support: issues with customer support not being helpful
- online_ordering: issues with ordering, website speed, or checkout process
- product_quality: issues with product quality or description
- shipping_and_delivery: issues with slow shipping or not receiving an order
- other_off_topic: a department could not be identified

Only respond with JSON that includes the sentiment and the department based
on the <examples> provided.
</instructions>

<examples>
User: Thank you @AcmeCorp! This new shampoo has been great!
Assistant: {"sentiment"="positive","department"="product_quality"}

User: My order from @AcmeCorp never arrived and customer service wasn't helpful.
Assistant: {"sentiment"="negative","department"="customer_support"}

User: I wouldn't trust @AcmeCorp.
Assistant: {"sentiment"="negative","department"="other_off_topic"}

User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great.
Assistant: {"sentiment"="positive","department"="shipping_and_delivery"}

User: The @AcmeCorp website is so slow. Every time I've tried to order I
can't even get through checkout.
Assistant: {"sentiment"="negative","department"="online_ordering"}
</examples>

User: Don't trust @AcmeCorp. It's been weeks and my order was never even shipped!
Assistant:
```

**响应**：`{"sentiment": "negative", "department": "shipping_and_delivery"}` ✅

**Prompt 结构分析：**

1. 指定 persona（online customer feedback expert）
2. 说明要做情感分析 + 部门路由
3. **给出有效的部门标签列表**（如 `customer_support`）**以及每个部门处理什么问题的描述**
4. 给出社媒评论 + 期望响应的示例

⚠️ **但仍有限制**：即使给大量示例，**响应格式也不被保证**。下一章的结构化输出才能保证一个代码可轻松消费的 JSON 格式。

> 💡 **什么时候该微调？** 如果模型对某类标签或任务不熟悉，我们可能需要提供**多到上下文窗口塞不下**的示例才能教会它。**这时微调才有意义**（Part IV 会看一个给收到的邮件打自定义标签的例子）。

### 📌 Prompt 中的分隔符（Delimiters）

我们用 XML 包住了 `<instructions>` 和 `<examples>`。**分隔符是分隔 prompt 中重要内容的有效方式，帮助 LLM 识别指令、上下文和示例。**

没有标准的分隔符，但 **XML、引号和 Markdown 都好用**。用你的模型和内容做实验。

## 5.4 思维链提示（Chain-of-Thought, CoT）

> 有没有注意到 LLM 有时能解决难题，却在简单事情上完败——比如数 "strawberry" 里有几个 r？

**LLM 不像我们那样天生会推理。** 人类会自动把问题拆成步骤，逐部分思考后再下结论。**LLM 默认试图基于见过的模式直接跳到最终答案。**

**CoT 鼓励模型一步步走过问题**，就像在编程面试的白板上那样。模型边解题边解释推理，这通常能改善响应质量。

> **这是 agent 中最常用的提示技巧之一**——它让模型能推理出达成用户目标所需的任务（Part V 详述）。

**它为什么有效？** 记住，模型预测出的 token 会被喂回上下文用于下一次预测。**这意味着模型本质上是在解决问题之前，先向自己解释了如何解决这个问题。**

### 两种触发 CoT 的简单方式

1. **明确告诉模型**："Think step-by-step."
2. **在 prompt 中提供展示多步推理的示例**

两种方式都引导模型**推理**而非**猜测**。

### CoT 的考量

| 考量 | 说明 |
| --- | --- |
| **推理有成本** | 更多 token = 更高延迟 + 更高费用 |
| **模型推理能力不同** | YMMV（你的体验可能不同） |
| **"大声思考"有风险** | 见下方警告 |

**关于推理模型**：OpenAI GPT-5 家族（为推理任务优化）即使不做重度提示也能解决分步问题。需要推理时，模型会在响应前生成**推理 token**（reasoning tokens）来"思考"。你甚至可以展开模型的"草稿纸（scratch pad）"看这些 token 和它如何得出结论——**这在你想验证模型响应时很有用**。

**隐藏成本**：托管 API 按输入输出 token 计费，"思考"生成的 token 越多，成本越高；这些额外 token 也因响应变长而导致响应时间更长。

### 替代方案：Chain of Draft（CoD）

CoD 试图克服 CoT 的缺点，**鼓励 LLM 只草拟推理所需的核心思路**。实现很简单：

> "Think step-by-step but keep only a minimal draft for each step, with five words at most."

能达到相当的性能，**但在高强度推理任务上可能不够**。

> ⚠️ **生产环境警告**：让模型用 CoT "大声思考" 可能适得其反。**分步文本可能意外泄露敏感数据、内部假设或偏见。** 许多系统使用 **hidden CoT**——模型在内部推理（"草稿纸"式），但只把最终答案返回给用户。

## 5.5 提示链（Prompt Chaining）

**Prompt chaining 把一个复杂请求拆成一系列聚焦的步骤和 prompt，把每一步的输出传给下一步。** 像在代码中组合小函数一样，逐步编排模型，从而在整个工作流中获得更好的模块化、可见性和控制力。

| 好处 | 说明 |
| --- | --- |
| **限定范围的子任务** | 每个 prompt 只干一件事（分类、抽取、推理、格式化），模型永远不必一次面对整个问题 |
| **显式的 I/O 契约** | 为每一步定义输入输出 schema，便于校验、替换或复用 prompt，无需重写整条链 |
| **调试直观** | 最终答案错了，检查中间输出定位失败阶段，而不是在一个巨型 prompt 里瞎猜 |
| **组件复用** | 一个测试良好的"抽取邮件字段" prompt 可以零改动地用在工单分诊和销售线索自动化两处 |
| **更低的 token 负载和延迟** | 每个 prompt 只看它需要的数据，相比一体化超大 prompt 节省上下文窗口、加快推理 |
| **内建护栏** | 在步骤之间插入校验（如 JSON schema 确认、事实性打分），在错误级联前捕获 |
| **透明的推理** | 暴露中间理由，产生一条审计轨迹——对微调、合规审查和向干系人解释极有价值 |

> 系统靠这个模式来编排 RAG 流水线、agent 等（见第 8 章）。

## 5.6 实用技巧与最佳实践

### 1. 聚焦正面表述，避免负面表述

给模型**清晰的正面指令**，而不是 "Don't do X" 的规则。

> **负面措辞迫使模型停下来推断你意思的反面，容易出错。正面命令更短、更容易检查，也帮助模型更一致地遵循指令。**

❌ "Do not include `sentiment:` in your response."
✅ "Respond only with the sentiment value: positive, neutral, or negative."

### 2. 和模型一起打磨你的 prompt（Leaning into bias）

每个 AI 模型都有基于训练数据的内建偏见——**你可以利用它**。

- 先问模型：**为了得到我想要的结果，我该怎么改进这个 prompt？** 你可以给它输入输出示例加指令，让它生成一个有用的 prompt。
- 做**分类任务**时，先问模型**它会怎么给数据打标签**。它给的标签基于它的训练偏见。**如果你能直接用它给的标签，或转换成你需要的，通常能得到更准确的结果——这叫"顺着偏见走（leaning into bias）"。**

比如情感分析：先给一句话，**不给 positive/negative/neutral 这些标签**，直接问模型情感是什么，看它自己会用什么词。

### 3. 把 prompt 当代码对待

好的软件工程师懂版本控制的价值：**只要跑通了，哪怕是很小的增量变更，就提交。** 这给了你重构、实验、彻底换路的自由，因为你总能回退到可用版本。

**对 prompt 一视同仁** —— 用你喜欢的 VCS（如 Git）或专门的提示工程工具。

### 4. 实验不同的 prompt 变体

**措辞方式能彻底改变模型响应的质量和准确性。** 测试同一 prompt 的多个变体能帮你找到最适合你任务的结构。也可以试不同模型。

可以自己做，也可以用 **PromptLayer** 这类工具并排比较多个 prompt 变体。

**常见的 prompt 比较与测试方法：**

| 方法 | 说明 |
| --- | --- |
| **A/B testing** | 两个 prompt 版本正面对决，看哪个响应质量更高 |
| **Human review loops** | 抽样输出，让领域专家评价清晰度、正确性和语气，捕捉自动指标漏掉的问题 |
| **Cross-model evaluation** | 同一 prompt 发给多个模型（GPT-5 mini、Claude Haiku 4.5、Llama 3.2），找出最符合你需求的 LLM |
| **Regression baselines** | 锁定一对"已知良好"的 prompt-模型作为基线，定期重跑以检测更新后的质量漂移 |
| **Automatic quality metrics** | 文本相似度用 BLEU 或 ROUGE，分类任务用 accuracy/F1，无需人工审查就能打分 |

## 本章小结

| 技巧 | 核心 |
| --- | --- |
| **Instruction prompting** | 简洁、正面的命令驱动数据抽取、PII 脱敏、合成数据生成，无需手写解析器或脆弱正则 |
| **Persona prompting** | 赋予角色隐式收窄模型范围、设定语气、降低 token 开销 |
| **Zero/One/Few-shot** | 在 prompt 中嵌入示例，教会模型领域特定的标签或响应格式 |
| **Chain-of-Thought** | 鼓励模型逐步思考，用更高 token 成本换更透明的逻辑 |
| **Chain of Draft** | CoT 的精简版，控制延迟和开销 |
| **Prompt chaining** | 类比代码中的函数组合，增强模块化、复用性和可审计性 |
| **最佳实践** | 正面表述、与模型协作迭代、prompt 当代码做版本管理、A/B 测试防止静默质量漂移 |

1. 把情感分析 prompt 做成 **zero-shot、one-shot、few-shot 三个版本**，记录每个版本正确分类的社媒帖子数量。
