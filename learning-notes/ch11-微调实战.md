## 11.1 选择要微调的模型

> **微调的一个关键优势：让一个更小的模型（参数更少）在特定任务上超越一个大型通用模型（数十亿参数）。**

**本章微调两个模型：**

| 模型 | 类型 |
| --- | --- |
| `distilbert/distilbert-base-uncased` | **预训练分类模型** |
| `Qwen/Qwen2.5-0.5B-Instruct` | **LLM** |

**衡量方式**：测量微调前后的准确率，并与一个更大的模型做基线对比。

## 11.2 建立基线（Baseline）

> **在开始微调前，必须了解我们选的模型在没有针对我们数据集做任何专门训练时，在邮件分类任务上表现如何。这个初始性能水平就是基线。**
>
> **有了清晰的基线，我们才能准确衡量微调后取得的真实影响和性能提升。**

**用 zero-shot 分类建立基线**：让模型纯粹基于其预训练的通用知识来分类邮件，**prompt 中不提供任何标注示例**。

**在三个模型上做 zero-shot 测试**：两个要微调的模型 + 一个强大的大型商业 LLM（Google Gemini）作为对比。

## 11.3 微调分类模型（DistilBERT）

> 对应代码：`part4/03-finetune-classificationModel.ipynb`

### 导入

```python
from transformers import AutoModelForSequenceClassification
from transformers import AutoTokenizer
from transformers import TrainingArguments, Trainer
from transformers import DataCollatorWithPadding
from datasets import load_from_disk
import numpy as np
import evaluate
```

| 导入项 | 作用 |
| --- | --- |
| `AutoModelForSequenceClassification`、`TrainingArguments`、`Trainer` | 核心模型和训练流程 |
| `AutoTokenizer` | 处理文本 tokenization |
| `DataCollatorWithPadding` | 准备数据批次 |
| `load_from_disk` | 加载我们保存的数据集 |
| `numpy` | 数值运算，这里主要用于指标计算 |
| `evaluate` | 加载标准评估指标 |

### 加载 tokenizer

```python
model_id = "distilbert/distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_id)
```

> ⚠️ **tokenizer 必须与模型匹配**，才能基于模型的预训练把文本处理成模型理解的数值输入。

### 预处理数据集

```python
def preprocess_function(examples):
    # Apply the tokenizer to the 'text' column,
    # truncating sequences that are too long
    return tokenizer(examples["text"], truncation=True)

# Load the dataset saved from the data preparation step
dataset = load_from_disk("./data/mail_dataset_labeled")

# Apply the preprocessing function to the entire dataset using map for efficiency
tokenized_dataset = dataset.map(preprocess_function, batched=True)
```

> **`map` 方法配合 `batched=True` 高效地把 `preprocess_function` 应用到成批的示例上**，为数据集各切分中的每个示例添加数值 token ID、**attention mask** 和其他必要输入。
>
> 📌 **Attention mask（注意力掩码）** 是二进制映射，**告诉模型哪些 token 是需要处理的有意义数据，哪些是计算时应忽略的 padding。**

### 动态 padding

> **Transformer 模型要求一个 batch 内的输入序列长度相同。** 由于我们的邮件摘要即使 tokenize 后长度也不一，我们用 `DataCollatorWithPadding`——**它会取一批 tokenized 的示例，动态地用特殊 padding token 填充较短的序列，让它们都匹配该批次中最长序列的长度。**

```python
data_collator = DataCollatorWithPadding(tokenizer=tokenizer)
```

### 定义评估指标

```python
accuracy = evaluate.load("accuracy")

def compute_metrics(eval_pred):
    # The Trainer provides predictions and labels during evaluation
    predictions, labels = eval_pred
    # Get the predicted class ID (the one with the highest probability)
    predictions = np.argmax(predictions, axis=1)
    # Use the loaded accuracy metric to compare predictions to true labels
    return accuracy.compute(predictions=predictions, references=labels)
```

### 标签映射

> **需要确保模型理解它输出的数值 ID 与我们邮件类别的有意义文本标签之间的关系。**

```python
label2id = {
    "IN_Bank":   0,
    "IN_School": 1,
    "US_Bank":   2,
    "US_School": 3
}

id2label = {
    0: "IN_Bank",
    1: "IN_School",
    2: "US_Bank",
    3: "US_School"
}
```

### 加载预训练模型

```python
model = AutoModelForSequenceClassification.from_pretrained(
    model_id, num_labels=4, id2label=id2label, label2id=label2id)
```

因为任务是分类，用 `AutoModelForSequenceClassification`。加载时告诉模型**输出标签数量（这里是 4）**并提供 ID↔标签映射，**让模型能正确解读数值预测。**

### 超参数（Hyperparameters）

> **模型训练需要用到大量设置，称为超参数（hyperparameters）。这些设置控制训练如何运行**——模型学得多快、一次处理多少数据、遍历数据集多少次。

```python
training_args = TrainingArguments(
    output_dir="trainer_output/my_mail_classifier",
    learning_rate=2e-5,
    per_device_train_batch_size=8,
    per_device_eval_batch_size=8,
    num_train_epochs=3,
    weight_decay=0.01,
    eval_strategy="epoch",
    save_strategy="epoch",
    load_best_model_at_end=True,
    push_to_hub=False,
    report_to="none",
)
```

| 参数 | 说明 |
| --- | --- |
| `output_dir` | 模型检查点和训练结果保存的目录 |
| `learning_rate` | **控制模型在训练中更新参数时迈的步子大小** |
| `per_device_train_batch_size` | 每个可用设备（如 GPU）上一次处理的训练示例数。**更大的 batch 需要更多内存，但有时能加快训练** |
| `per_device_eval_batch_size` | 同上，但用于评估数据集 |
| `num_train_epochs` | **训练过程遍历整个训练数据集的总次数** |
| `weight_decay` | **正则化技术**，通过惩罚模型中过大的权重来帮助**防止过拟合** |
| `eval_strategy="epoch"` / `save_strategy="epoch"` | 告诉 Trainer **在每个训练 epoch 结束时**在评估集上评估性能并保存检查点 |
| `load_best_model_at_end=True` | **训练完成后加载在评估集上取得最佳性能的检查点** |
| `push_to_hub=False` | 防止 Trainer 自动把训练好的模型上传到 Hugging Face Hub |
| `report_to="none"` | 禁用向外部服务报告训练指标 |

### 组装 Trainer 并训练

```python
trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset["train"],
    eval_dataset=tokenized_dataset["validation"],
    tokenizer=tokenizer,
    data_collator=data_collator,
    compute_metrics=compute_metrics,
)

trainer.train()          # 一行代码启动整个技术微调流程
```

### 保存模型

```python
model_path = "models/my_mail_classifier"
trainer.save_model(model_path)
```

**这样以后可以直接加载使用我们的专用邮件分类器，不必重新训练。**

> ⚠️ **使用微调后的模型时，要用 `text-classification` pipeline 任务，而不是 `zero-shot-classification`。**

## 11.4 微调 LLM 的前置概念

### 为什么不用提示工程？

**两个关键术语：**

- **Model weights（模型权重）**：神经网络或 ML 模型内部的数值参数。**权重在训练过程中被调整，共同表示模型从数据中学到的模式、特征和知识。它们决定模型如何处理输入信息以产生输出。**
- **Catastrophic forgetting（灾难性遗忘）**：发生在顺序学习（如微调）中——**在新任务上训练模型导致它突然或严重地丧失执行原先训练任务的能力。新学习干扰并覆盖了模型与旧数据或任务相关的既有知识和技能。**

| | 微调（Fine-tuning） | 提示工程（Prompt engineering） |
| --- | --- | --- |
| **工作方式** | **通过在新数据集上训练来更新 LLM 的权重**，使其适应特定任务或领域 | 精心设计输入 prompt 来引导 LLM 的输出，提供指令、上下文或示例 |
| **优点** | 相比提示工程可带来显著的性能提升<br>**让模型学到更深入的知识并适应特定数据分布**<br>能改善对新的相似任务的泛化<br>对模型行为提供更多控制 | **算力成本比微调低得多**<br>**不需要访问训练数据或修改模型权重**<br>对某些任务非常有效，尤其在熟练的 prompt 设计下 |
| **限制** | 算力成本更高、更耗时<br>需要访问训练数据和更多技术专长<br>**如果不小心，有灾难性遗忘的风险** | 需要精心设计和反复实验<br>**可能达不到微调的性能水平，尤其是复杂任务**<br>难以泛化到新任务或领域<br>**对模型内部知识和行为的控制有限** |

**用微调，当你有：**

- 对最高性能的需求
- **需要模型学习深入知识的复杂任务**
- 训练数据的访问权和微调的资源
- 需要让模型适应特定领域或任务

**用提示工程，当你有：**

- 有限的资源或时间
- 更简单的任务或需要快速方案
- **没有训练数据或微调能力**

> 💡 **微调就像给一个小而专门的工具打磨出适合特定工作的完美刃口。更大、更通用的工具或许能做很多任务，但一个微调过的小工具可以高效精准得多，运行起来也经济得多。**

## 11.5 PEFT 与 LoRA

### 常规微调 vs PEFT

**常规微调**（前面 DistilBERT 的例子）：**在新数据上训练，更新语言模型的所有参数。**

| ✅ | ❌ |
| --- | --- |
| 让模型学习新信息、适应新数据的特定特征 | **算力极其昂贵且耗时** |
| 尤其在数据充足时能带来显著性能提升 | **需要更多数据以避免过拟合** |
| 相对容易实现 | **导致灾难性遗忘** |

> 📌 **Overfitting（过拟合）**：模型把训练数据学得太精确了，**包括那个数据集独有的噪声和特定细节。模型本质上是在记忆训练示例而非捕获通用的底层模式。** 结果是在训练数据上表现极好，但在被要求对新的、未见过的数据做预测时表现显著变差。

**PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）**：

> **PEFT 方法向模型引入少量额外参数，而不是修改整个权重矩阵。这显著减少了可训练参数的数量，让微调过程更高效、算力成本更低。**
>
> 可训练参数更少 → 训练需要的内存和算力更少 → **训练时间更快，尤其对大模型。**

### PEFT vs 常规微调对比

| | PEFT | 常规微调 |
| --- | --- | --- |
| **何时用** | 数据或算力资源有限<br>需要更快的训练和部署<br>想最小化存储需求<br>**新任务与原始预训练任务相对相似** | 数据和算力资源充足<br>需要最大的性能提升<br>**新任务与原始预训练任务显著不同** |
| **优点** | 比常规微调更高效更快<br>**更不易过拟合，尤其在数据有限时**<br>减少微调模型的存储需求<br>**缓解灾难性遗忘** | 尤其在数据充足时能带来显著性能提升<br>相对容易实现 |
| **缺点** | 某些情况下可能达不到常规微调的性能水平<br>**需要仔细选择 target modules** | 算力昂贵且耗时<br>需要更多数据以避免过拟合<br>**可能导致灾难性遗忘** |

### LoRA（Low-Rank Adaptation）

> **LoRA 是 PEFT 方法之一。** 想象根据你喜欢的驾驶方式定制汽车引擎——**与其把它拆开重建，如果你只需要调整几个关键组件呢？这就是 LoRA 的想法。**
>
> 它像给引擎控制系统装一块小而专门的芯片。**这块芯片能轻松定制各种模式（eco、normal、sport），而不改变引擎本身。LoRA 的工作方式类似：向现有模型添加少量可调参数，实现高效微调而没有巨大开销。**

| 好处 | 说明 |
| --- | --- |
| **训练更快更便宜** | LoRA 的训练速度比全量微调**快得多**。调整的参数少得多，训练时间只需一小部分，**直接转化为更低的算力成本（GPU 小时费用更少）** |
| **降低硬件门槛** | 显著减少所需内存。**这是巨大的好处——它让在更容易获得的消费级硬件上微调巨型模型成为可能**，而不必依赖昂贵的顶级企业 GPU |
| **便携高效** | 不产生一个新的巨型模型（如 20GB），**LoRA 训练输出一个微小的"adapter"文件（通常只有 10–100MB）**。这让存储、分享和部署单个基座模型的多个微调版本变得极其容易 |
| **高质量结果** | **尽管高效，LoRA 达到的性能可与传统微调相当，某些情况下甚至更好。** 你得到全量微调的质量而没有高昂成本 |

### 参数量削减的数学

**LoRA 保持原始大层冻结（frozen），在它们旁边注入小型可训练的 adapter 层。**

> **LoRA 最重要的设置是 rank（秩），通常记作 `r`。这个值直接控制被添加到模型的微小 adapter 层的大小。**
> - **较低的 r** → adapter 层非常"窄"，增加的新参数更少
> - **较高的 r** → 允许可能更细致的适配，但增加了 LoRA 训练的参数数量

**举例：** 假设模型中某一层的权重矩阵是 **1,000 × 1,000 = 100 万参数**。

**LoRA 用 rank `r`（比如 r=5）不训练这 100 万，而是添加并训练两个小得多的矩阵：一个 `1000 × r`，一个 `r × 1000`。**

```
可训练参数 = (1,000 × r) + (r × 1,000)
r=5 时    = (1,000 × 5) + (5 × 1,000) = 5,000 + 5,000 = 10,000
```

**这一层原本的 100 万参数，LoRA 只需训练 1 万个。**

> **LoRA 把这个技术应用到模型中的多个关键层。把所有应用 LoRA 的层上相对少量的新增参数加起来，可训练参数总数从可能的数十亿戏剧性地降到几百万甚至几千**，使微调快得多、资源消耗少得多。

## 11.6 指令模板（Instruction / Chat Templates）

> 对应代码：`part4/04-chat-examples.ipynb`

> **虽然 LLM 被设计来理解人类语言，但它们并不总是被训练来解读以完全相同格式呈现的指令和对话历史。你 prompt 的具体结构——你如何界定用户输入、系统消息或之前的轮次——因模型而异。**
>
> **Instruction template（指令模板，也叫 chat template）就是特定 LLM 被训练来期望接收指令、上下文或聊天历史时所用的具体文本格式，包括特殊 token 和结构规则。**
>
> **使用你所用模型的正确模板，对确保模型正确理解你的输入并按预期方式响应至关重要。**

### 查看模板

```python
tokenizer = AutoTokenizer.from_pretrained(model_id)
print(tokenizer.get_chat_template())
```

**Qwen 的输出：**

```jinja
{% for message in messages %}
{% if loop.first and messages[0]['role'] != 'system' %}
{{ '<|im_start|>system You are a helpful assistant<|im_end|>' }}
{% endif %}
{{'<|im_start|>'+message['role']+' '+message['content']+'<|im_end|>'+' '}}
```


> 💡 **看仔细的话你会发现 role（system、user、assistant）就在模板里。当你和 ChatGPT 或 Gemini "对话"时，幕后消息就被转换成这种格式再发给模型。**

### tokenize 与 return_tensors

- **`tokenize=False`** —— 看到应用模板后生成的**实际文本输出**（模板字符串 + 你的消息 + 特殊 token）。**有助于可视化模型期望的确切格式。**
- **`tokenize=True`**（常为默认）—— 不仅按模板格式化文本，还**立即把格式化的文本送过 tokenizer，返回数值 token ID 列表**。
- **`return_tensors="pt"`** —— 输出格式化为包含这些数值 ID 和 attention mask 等必要输入的 **PyTorch tensors**，可直接喂给模型。

```python
tokenized_input = tokenizer.apply_chat_template(
    prompt,
    tokenize=True,
    return_tensors="pt"
)
```

```python
]

tokenized_input = tokenizer.apply_chat_template(
    prompt, tokenize=True, return_tensors="pt"
)

output_text = model.generate(tokenized_input, max_new_tokens=50)

print(tokenizer.decode(output_text[0], skip_special_tokens=True))
```

**输出：**

```
system
You are a helpful geography assistant.
You are able to answer questions about the world.
user
What is the capital of France?

The capital of France is Paris.
```

> - **`skip_special_tokens=True`** 确保只返回解码后的文本，不含任何特殊格式或 token
> - **`max_new_tokens`** 设置模型生成的新 token 数上限；**`min_new_tokens`** 设置输出序列的最小长度

### 定制生成响应的格式

**技巧：在格式化 prompt 的最末尾添加 assistant 角色标记，明确告诉模型现在轮到它生成文本了。**

**也可以用这个技巧让模型的输出以特定前缀开头：**

```python
prompt = [
    # ... system、user 消息
    {
        "role": "assistant",
        "content": "GA: "        # 期望响应以 "GA: " 开头
    },
]

tokenized_input = tokenizer.apply_chat_template(
    prompt, tokenize=True, return_tensors="pt"
)
output_text = model.generate(tokenized_input, max_new_tokens=50)
print(tokenizer.decode(output_text[0], skip_special_tokens=True))
```

**输出：**

```
system
...
user
What is the capital of France?
assistant
GA:
```

⚠️ **不太符合预期！为什么模型没有以 `GA:` 开头继续？为什么它换行了？**

### continue_final_message：控制生成从哪里开始

> **通常，chat template 会添加特殊 token 标记每条消息或每一轮的结束，引导模型完成它的想法或等待下一个输入。**
>
> **但对某些任务，你可能希望模型生成的文本是「继续 prompt 中提供的最后一条消息」，而不是开始一个由 assistant 角色 token 标记的全新轮次。**
>
> **`continue_final_message` 参数控制这一点，它允许你抑制最后一条消息后通常的回合结束信号，指示模型生成从上一条消息中断处直接流出的文本。**

```python
tokenized_input = tokenizer.apply_chat_template(
    prompt,
    tokenize=True,
    return_tensors="pt",
    continue_final_message=True,       # 关键
)
output_text = model.generate(tokenized_input, max_new_tokens=100)
print(tokenizer.decode(output_text[0], skip_special_tokens=True))
```

**输出：**

```
system
...
user
What is the capital of France?
assistant
GA: 09000 Paris, Île-de-France, France
```

> **这个配置把模型的行为从结构化的轮流对话转变为连续的文本补全模式。** 你现在让 LLM 能够精确地从你的 prompt 结束处接起叙述或逻辑线索。

## 11.7 构建 LLM 微调数据集

> 对应代码：`part4/05-finetune-dataset.ipynb`

### 训练/验证集：包含 assistant 回答

```python
label_names = ["IN_Bank", "IN_School", "US_Bank", "US_School"]

def convert_to_training_messages(dataset):
    messages = [
        [
            {"role": "system",    "content": message_system},
            {"role": "user",      "content": f"Categorise: {ds['text']}"},
            {"role": "assistant", "content": f"Category: {label_names[ds['label']]}"}
        ] for ds in dataset
    ]
    texts = [
        tokenizer.apply_chat_template(message, tokenize=False)
        for message in messages
    ]
    return {"text": texts}
```

```python
dataset = load_from_disk("./data/mail_dataset_labeled")

ds_train = convert_to_chat_messages(dataset["train"])
ds_val   = convert_to_chat_messages(dataset["validation"])

ds_train = Dataset.from_dict(ds_train)
ds_val   = Dataset.from_dict(ds_val)
```

> 💡 **为什么用 `Dataset.from_dict`？** 因为 `convert_to_chat_messages` 返回的是标准 Python 字典（或字典列表），而不是 Hugging Face `Dataset` 对象。**这一步本质上是把处理好的数据"重新打包"回训练所需的格式。**

### 测试集：不含 assistant 回答

> ⚠️ **测试集不应用这套逻辑，因为我们不想在 prompt 中包含最后的 assistant 块。相反，我们希望训练好的模型给出响应——这由 `add_generation_prompt=True` 触发。**

```python
def convert_to_prompting_messages(dataset):
    data = []
    for ds in dataset:
        message = [
            {"role": "system", "content": message_system},
            {"role": "user",   "content": f"Categorise: {ds['text']}"}
        ]
        chat_message = tokenizer.apply_chat_template(
            message,
            tokenize=False,
            add_generation_prompt=True,        # 关键
        )
        data.append({
            "text": chat_message,
            "label": ds["label"]
        })
    return {"items": data}

ds_test = convert_to_prompting_messages(dataset["test"])
ds_test = Dataset.from_dict(ds_test)
```

### 合并保存

```python
ds_combined = DatasetDict({
    "train":      ds_train,
    "validation": ds_val,
    "test":       ds_test
})

ds_combined.save_to_disk("./data/llm_mail_dataset")
```

## 11.8 用 LoRA 训练 LLM

> 对应代码：`part4/06-finetune-llm.ipynb`

**四个步骤：**

1. 定义 LoRA 配置
2. 把配置应用到模型
3. 创建训练参数
4. 训练

### 1. LoraConfig

```python
from peft import LoraConfig

lora_config = LoraConfig(
    r=4,
    lora_alpha=8,
    lora_dropout=0,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    modules_to_save=["lm_head"]
)
```

| 参数 | 说明 |
| --- | --- |
| **`r`** | **LoRA rank（秩）**。最关键的参数，控制添加到模型层的小 adapter 矩阵的大小，因而决定可训练参数数量。**更低的 r = 更少参数，但可能减少复杂适配的能力** |
| **`lora_alpha`** | **缩放因子**，调整 LoRA 层学到的更新的幅度。**通常按比例设为 r 的倍数（如等于 r 或 2×r）**，控制 LoRA 适配对原模型行为的影响程度。**实际应用的缩放通常是 `lora_alpha / r`** |
| **`lora_dropout`** | 训练时应用到 LoRA adapter 层的 **dropout 率**。dropout 技术在每个训练步中随机忽略一部分连接，**帮助防止小的 LoRA adapter 过度拟合训练数据** |
| **`bias`** | 控制 target layer 中 bias 项在 LoRA 训练中如何处理。**`bias="none"` 表示 `target_modules` 指定层中的 bias 参数不被训练，保持冻结在预训练值** |
| **`task_type`** | 告诉 peft 库你在为哪种下游任务微调。**`CAUSAL_LM` 表示因果语言建模，即大多数文本生成 LLM 的标准任务（基于前面的 token 预测下一个）** |
| **`target_modules`** | **指定 LoRA adapter 矩阵应注入到预训练基座模型中的哪些子层/模块**。Transformer 中的常见目标是**注意力机制中的权重矩阵**（query `q_proj`、key `k_proj`、value `v_proj`、output `o_proj`）和**前馈网络中的层**（`gate_proj`、`up_proj`、`down_proj`）。**只针对特定的重要模块，让 LoRA 的可训练参数远低于全量微调** |
| **`modules_to_save`** | 指定额外的模型组件（如 `lm_head`），**它们的原始权重也会变成可训练的并与 LoRA adapter 一起保存**。**微调 `lm_head` 至关重要，因为它直接影响模型的输出概率**，能从针对你特定任务的直接适配中受益 |

> 📌 **Transformer 层的内部结构**
>
> Transformer 模型由重复的层构成，每层主要由两个协同工作的组件组成：**注意力机制（attention mechanism）和前馈网络（feed-forward network, FFN）**。
>
> **注意力机制**是模型在处理任一个词时关注输入文本不同部分的方式。**它让模型能看序列中的其他词，判断哪些对理解当前词在上下文中的含义最重要或最相关。这对理解相隔很远的词之间的关系至关重要。**
> - 注意力机制内部有具体的线性投影层：`q_proj`、`k_proj`、`v_proj`——它们把输入变换成计算注意力所用的 **query、key、value** 表示
> - `o_proj` 层处理注意力步骤的组合输出
> - **当你在 LoRA 的 `target_modules` 中看到这些名字，意味着 LoRA 在学习微妙地调整模型计算和处理注意力的方式**，为你的微调任务专门化这一核心聚焦机制
>
> **前馈网络（FFN）** 在注意力机制处理完词之间的关系后接管。**它像标准神经网络层，但关键点在于它完全独立于序列中其他词地处理每个词的表示。** FFN 取单个词的富上下文信息，跑过几个变换步骤，添加非线性。
> - LoRA 常见的 FFN 目标层：`up_proj`、`down_proj`，有时还有 `gate_proj`
> - **这些层扩展（`up_proj`）和收缩（`down_proj`）表示的维度**，让模型能进一步处理和变换注意力学到的信息
> - **在这里应用 LoRA 帮助模型为微调任务学习新的方式来内部处理和变换这些单个 token 表示**

### 2. 应用到模型

```python
from peft import get_peft_model

peft_model = get_peft_model(
    model,
    lora_config,
)
```

> **`get_peft_model` 接收你的原始基座模型和 `lora_config` 对象，按 LoRA 配置修改基座模型的架构。这包括：**
> 1. **把小型可训练的 LoRA adapter 层注入你在 config 中定义的特定 `target_modules`**
> 2. **重要的是，自动"冻结"（设为不可训练）基座模型中绝大多数原始参数**
>
> **返回的 `peft_model` 现在是基座模型的参数高效版本**，专门为使用 LoRA 方法微调而准备。**它的行为就像普通的 Hugging Face 模型**，可以直接传给 Trainer 或用于推理，**但在内部，训练过程中只有 LoRA adapter 中的一小部分参数会被更新，带来显著的算力节省。**

### 3–4. 训练（SFTTrainer）

> **用 Hugging Face `trl`（Transformer Reinforcement Learning）库的 `SFTTrainer`。这个专门的工具包通过提供监督微调和其他对齐技术的高层工具，简化了后训练过程。**
>
> **`SFTTrainer` 在配合 LoRA 这类 PEFT 技术时特别方便**，它简化了从配置训练参数到用你的特定模型和数据集初始化 trainer 的过渡。

```python
from trl import SFTTrainer, SFTConfig

training_args = SFTConfig(
    output_dir="trainer_output/my_mail_classifier_llm",
    report_to="none",
    overwrite_output_dir=True,
    do_train=True,
    learning_rate=2e-4,
    num_train_epochs=3,
    bf16=False,
    fp16=False,
)

trainer = SFTTrainer(
    model=peft_model,
    args=training_args,
    train_dataset=dataset["train"],
    eval_dataset=dataset["validation"],
)

trainer.train()
```

| 参数 | 说明 |
| --- | --- |
| `output_dir` | 训练好的模型检查点、日志和其他输出的保存位置 |
| `report_to` | 设为 `none` 防止向外部平台报告训练指标 |
| `overwrite_output_dir` | 设为 `True` 允许 Trainer 删除并重建已存在的 `output_dir` |
| `do_train` | 确认应执行训练过程 |
| `learning_rate` | 设置模型优化器的初始学习率 |
| `num_train_epochs` | Trainer 遍历整个训练数据集的次数 |
| `bf16=False` / `fp16=False` | **禁用混合精度训练**（BFloat16 / Float16），模型将以完整的 float32 精度训练 |

**保存：** 调用 `trainer.save_model` 并给出目标路径。**Trainer 和 peft 库确保基座模型的冻结权重、新训练的 LoRA adapter 权重和配置一起保存在该目录中**，形成一个完整的包，随时可加载使用。

> ⏱ **训练时长**
>
> 取决于你的系统和参数，训练可能从几分钟到几小时不等。**一个主要影响因素是硬件：GPU 上训练比 CPU 快得多——GPU 被设计来处理 ML 模型所需的并行计算。**
>
> **书中的设置，训练过程大约耗时 4.5 小时。** 请耐心，并随意实验不同的训练参数以找到最适合你需求的配置。

## 本章小结（Part IV 总结）

**你走了两条不同但强大的路：微调专用分类模型（DistilBERT）和通过现代高效技术适配 LLM（Qwen2.5）。**

| 阶段 | 要点 |
| --- | --- |
| **建立 zero-shot 基线** | 在任何训练前用原始数据测试 Gemini 和更小的 LLM，**学会衡量改进空间并为专用模型设定清晰目标** |
| **数据准备** | 把数据集转换成模型需要的特定格式——**编码器的简单 tokenization，或 LLM 的复杂 chat template** |
| **高效适配** | 通过引入 LoRA 解决 LLM 的巨大算力成本，**用 PEFT 方法更快、更省资源地定制巨型模型** |
| **执行与评估** | 用 Hugging Face 生态（`transformers`、`peft`、`trl`）配置训练参数并执行微调，**通过评估结果证明工作的价值** |

## 练习

1. **调整超参数**：试着调整 `learning_rate`、`num_train_epochs` 或 LoRA rank（`r`）。**观察这些变化如何影响训练速度、内存消耗和模型最终的"智能"。**
2. **换基座模型**：从 Hugging Face Hub 选不同的基座模型——也许是 Gemma 或 Llama 的某个变体——应用同样的流水线。**比较不同架构对相同数据的响应是最好的学习方式之一。**
3. **超越简单准确率**：探索 **precision、recall、F1 score** 等指标，看你的模型是否偏向某些类别或在特定类型数据上表现挣扎。
4. **实验 prompt 格式**：对 LLM，实验 system prompt 或 user 指令格式。**你"要求"模型学习的方式上的小变化，可能带来性能的显著提升。**
